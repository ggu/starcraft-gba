# Diamond placement microbenchmark

This asset-free ARM microbenchmark runs identical source and flags except `GBA_DIAMOND_ROM`; both binaries use the unchanged `common/gba.ld` assertions. It draws four deterministic batches, including clipped and off-screen coordinates, then hashes the entire Mode 4 back buffer. Run the Makefile and `measure.py` under the project's native-build lock. The runner must match the pinned SHA-256 in the script; its legacy protocol exposes allowlisted writes, but this script issues only breakpoint, continue and read commands. Outputs are ignored and contain no imported assets.

On the 2026-11-06 local run, with mGBA runner SHA-256 `0ee4cae88eea4dca4c744ab771fb5fa0b630def593f970c0ca89cc41594cb74d`, three runs produced the same cycle counts. IWRAM ARM versus ROM Thumb respectively: one off-screen diamond 2,096 vs 2,493; 32 mixed diamonds 170,517 vs 250,512; 128 mixed diamonds 721,317 vs 1,038,748; and 128 with Y clipping 677,822 vs 935,822. Final back-buffer checksums matched for each pair. The linked IWRAM function is 464-byte ARM code at `0x03000fd4`, called via a 12-byte Thumb-to-ARM veneer; the ROM function is 358-byte Thumb code at `0x08000510`. Thus this compares the complete existing compile option, including code generation and addresses, rather than isolating physical memory alone. Both maps pass the guards.

These are synthetic call-batch measurements, not a Cocoon, HUD, ordinary play, whole-game FPS, physical-device, or runtime stack qualification. A checksum match plus the existing HOST graphics oracle does not substitute for full scene equivalence. The candidate remains default-off pending whole-scene and stack evidence.
