# ares v148 headless N64 feasibility

A source-only review of the official ares `v148` tag resolved to commit [`0aafd85789215e84e1e43415c07d4c88461b7899`](https://github.com/ares-emulator/ares/tree/0aafd85789215e84e1e43415c07d4c88461b7899). The installed app identifies itself as v148, but this review does not establish that its binary was built from those exact source bytes or settings. No ares build, emulator launch, controller input, game-memory read or new screenshot was performed. The owned N64 ROM and existing references were not modified.

The app's embedded usage text lists `--system`, `--setting`, `--settings-file`, `--no-file-prompt`, `--kiosk` and related presentation controls; it does not advertise headless, scripted controller input or frame capture switches. `--kiosk` is a minimal UI mode. The [desktop screenshot hotkey](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/desktop-ui/input/hotkeys.cpp#L98) sets a request consumed by the [video callback](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/desktop-ui/program/platform.cpp#L80); a screenshot-directory setting is not a capture command. The retained local polling shim intercepts an OS key-state function and is not an emulator controller API. This proposal does not use that shim or any other OS input automation.

## Source-level integration path

The source builds [`ares::ares` as a static CMake target](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/CMakeLists.txt#L1) and `ares::mia` as another target. [`ares::Platform`](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/ares/platform.hpp#L16) supplies virtual `pak(Node::Object)`, `input(Node::Input::Input)`, `video(Node::Video::Screen, const u32*, u32 pitch, u32 width, u32 height)` and `audio(Node::Audio::Stream)` callbacks through the global `ares::platform`. A separate custom C++ frontend could implement those callbacks, but these are source-integration interfaces, not an established stable ABI or a supported ready-made full-console headless executable.

The [desktop N64 loader](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/desktop-ui/emulator/nintendo-64.cpp#L57) creates `mia::Medium::create("Nintendo 64")`, loads a ROM, creates and loads `mia::System::create("Nintendo 64")`, sets N64 options, calls `ares::Nintendo64::load(root, "[Nintendo] Nintendo 64 (NTSC)")`, allocates and connects `Cartridge Slot` and `Controller Port 1` / `Gamepad`, then powers the root. The `Platform::pak` implementation must return the appropriate system and cartridge VFS directories; [the desktop mapping](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/desktop-ui/emulator/nintendo-64.cpp#L403) identifies those nodes. The [MIA system loader](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/mia/system/nintendo-64.cpp#L7) supplies embedded PIF resources; the [medium loader](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/mia/medium/nintendo-64.cpp#L86) constructs the cartridge manifest and pak. MIA can access saves next to the ROM by default: set an isolated `mia::setSaveLocation` before loading, verify the actual path, and never reuse the user's saves.

The [gamepad read path](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/n64/controller/gamepad/gamepad.cpp#L354) calls `platform->input` for X/Y, D-pad, A/B, C buttons, L/R/Z and Start. An input callback can identify the connected controller and set `Node::Input::Button::setValue(bool)` and `Axis::setValue(s64)` from a bounded emulated-button script, without synthesizing host OS events. Pin exact axis values and make unsupported ports neutral. Input is sampled when the emulated controller is polled, not necessarily once per visible frame.

`root->run()` invokes the [N64 CPU loop](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/n64/cpu/cpu.cpp#L37), which normally runs until VI refresh but can return on a debugger stop; that is not proof of a StarCraft game-update tick. The VI calls `screen->frame()` on its timing path. [`Screen::frame` and refresh](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/ares/node/video/screen.cpp#L202) are threaded in this revision, and the [callback receives](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/ares/node/video/screen.cpp#L349) a processed `u32` buffer, pitch and viewport. A harness needs a synchronized, bounded copy while the callback data is valid; it must explicitly observe callback order, size, crop and field behavior instead of equating callback count with game frames. It must also handle attached audio streams and drain or safely discard their data without inducing a deadlock or unbounded buffering.

## Rendering and limits

The N64 CMake target [enables Vulkan and paraLLEl-RDP](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/n64/CMakeLists.txt#L29); the macOS source looks for MoltenVK. At runtime the [Vulkan loader](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/ares/n64/vulkan/vulkan.cpp#L46) explicitly reports `No RDP rendering support` when disabled or initialization fails. The source contains a non-Vulkan RDP/VI fallback, but useful StarCraft frames, equivalence to the installed paraLLEl-RDP configuration, Vulkan operation without a window, and performance are not established. The vendored paraLLEl-RDP `rdp-validate-dump` is a headless **RDP dump** validator, not a complete N64 boot/input frontend.

The top-level [license file](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/LICENSE) permits ares source use with its notice, and enumerates additional components with their own terms. A derived build must retain applicable notices for all linked and vendored components. The source checkout and proprietary ROM/art must stay outside public project commits.

## Smallest honest next test

First inspect the exact build prerequisites and produce an isolated opt-in source-integrated harness, keeping the official checkout immutable. It should authenticate the owned ROM hash, set isolated saves before MIA loading, construct the same NTSC system and renderer options, bound run steps/time/frame count/output bytes, and emit only recorded emulated-button masks plus callback frame metadata and hashed/copied frame buffers. Do not expose debugger writes, guest-memory writes, savestate injection or host key/event mechanisms. On startup fail closed if system/cartridge/controller setup or renderer initialization fails.

A first controlled experiment would compare two fresh runs with identical neutral input, then a small A/Start/release sequence against neutral, checking input callback identities and button polls, video callback count/order/pitch/geometry and frame hashes. Synchronize asynchronous video without reading freed buffers, and record exact source, toolchain, renderer, ROM, configuration and output hashes. Only then compare representative native frames and settings with a previously verified interactive ares capture. A successful boot or matching screenshot does not establish N64 timing, actor semantics or game parity. No such harness has been built or run in this review.

## Local prerequisite inventory

The local machine reports an Apple M3 Pro GPU with Metal 4, Apple Clang 21, Xcode macOS SDK, CMake 4.4.4 and Ninja. The installed v148 app includes an arm64/x86_64 `libMoltenVK.dylib` (SHA-256 `432e8880bc83e068f26e47928d01cb34c501694769e8527f34118c93946e6f99`); it is not registered in the local `pkg-config` search path. Neither `glslangValidator` nor `glslc` was found on PATH. The source tree includes PIF resources, libco, sljit, Vulkan headers and a precompiled paraLLEl-RDP shader bank. These observations do not prove an isolated build can link, initialize MoltenVK without a window, or produce correct video. Runtime library paths, signing, transitive dependencies and renderer behavior remain open.

The v148 macOS CMake setup defaults to fetching `ares-deps` and writing beneath the source checkout; [`ARES_SKIP_DEPS`](https://github.com/ares-emulator/ares/blob/0aafd85789215e84e1e43415c07d4c88461b7899/cmake/common/dependencies_common.cmake#L5) disables that fetch. The root CMake project configures desktop-related subdirectories even when only a core target is wanted, so the available app libraries do not by themselves establish a minimal dependency closure. The MoltenVK finder accepts an explicit library path, but that and any isolated `@rpath` solution need a bounded build proof. The source checkout is about 43 MiB and the host had about 132 GiB free at inspection; build output size and duration are unknown. No configuration, dependency install, build or runtime test was performed for this inventory.
