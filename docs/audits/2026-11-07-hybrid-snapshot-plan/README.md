# Hybrid snapshot preparation

This is source preparation, not an executable observer or a native result. The separate proposed role would use the existing authentic same-process official JIT state restore into interpreter mode and retain its before/after cache-aware equality check. It must admit snapshot commands only after the transition, with both recompilers and homebrew mode off, 8 MiB RDRAM, and no more than three snapshots. The existing visual role remains unchanged. The new pure contract and asset-free fixture express only these admission conditions; they are not yet connected to the frontend or wrapper.

For each requested snapshot, use the existing `sc64_read_ram` cache-hit/direct-RDRAM-miss routine and reject duplicate cache aliases. Capture into private scratch, discard it on any conflict, and create the output only after the entire read succeeds. Record the exact completed input step and conflict status without claiming that the step is a game clock. The bounded role must pin an ordinary controller plan, authenticate its command log, require its exact three snapshot/checkpoint positions, independently require the requested GPU frames, and recheck all source, binary, ROM and library pins. No external state, arbitrary guest writes or MMIO reads are admitted. The capture plan and the button semantics remain to be reviewed before implementation or execution; three snapshot positions alone do not prove independent actor selection or STOP.

Owned-output budgeting must include the 33,554,432-byte ROM copy, at most 25,165,824 snapshot bytes, and at most 2,097,152 framebuffer bytes: 60,817,408 bytes before metadata. The existing 63 MiB pre-manifest guard permits 5,242,880 bytes for all logs, save files, CSV, inventory and other outputs, subject to periodic monitoring; 64 MiB remains the overall limit. Each snapshot is at most 8 MiB, matching the existing 8 MiB hard per-file cap. The existing 175-second child / 180-second supervisor limits, 5 GiB reserve, native lock, and stopped-child diagnostic policy remain unchanged. These are admission limits, not a guarantee that the interpreter can complete the control sequence in time or that external host caches are counted.

A future build needs a new compiled-binary pin and asset-free tests for visual-role rejection, transition/flags, three-snapshot maximum, conflict with no partial published file, exact CSV/step validation, time/output/reserve cleanup and immutable input checks. A future run requires separate review and authorization. Actor identity, movement or STOP semantics, native clock and full fresh-reset interpreter timing remain unproven.
