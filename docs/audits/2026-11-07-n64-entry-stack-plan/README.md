# Bounded selected-Probe entry stack: source plan

This is a source-only proposal, not a stack capture or a game-clock result. In the qualified entry run, `8000c390` begins with MIPS instruction `27bdffe0` (`addiu sp,sp,-32`), whose rs field is register 29. The already qualified copied-core instruction-begin callback passes the pre-instruction value of that rs register as its base argument. At this entry that value is therefore the guest SP before the callee's prologue, without a new core hook. The observed caller path enters from RA `8013b418`; the nearby candidate caller prologue at `8013b3f8` allocates 0x28 bytes and stores its own RA at offset 0x20 from its SP before its call at `8013b410`. If that path and stack state are intact, the 32-bit saved caller return address lies at pre-callee SP + 0x20. Its value is a candidate return address, not yet a verified function or update loop.

A separate observer-only role could reuse the existing copied core archive and callback ABI, preserving the old qualified observer and all prior roles. After the existing full 8 MiB baseline hash and identity gates, it would accept only an actual `8000c390` entry whose a0 equals the authenticated selected Probe record. At most eight records would copy 256 bytes from the pre-prologue SP through the existing cache-aware read routine, only after validating canonical KSEG alias, alignment, physical RDRAM range and bounds. Cache-alias conflict must discard scratch and be explicitly recorded as failure, with no output published from the failed read. The observer must not read MMIO, alter guest memory or CPU state, or treat the view as necessarily atomic against DMA. It must keep actual entry PC, RA, SP, input step and capture status with each bounded window; additional entries beyond the cap must be counted rather than silently treated as complete.

Eight fixed 288-byte records would add at most 2,304 bytes to the existing maximum 196,608 bytes of CPU stores and 57,344 bytes of entry records, for 256,256 bytes before any format header, within the existing 256 KiB combined allowance if the header and wrapper caps are explicitly enforced. The existing 4,322-step plan, three 8 MiB views, two frames, 8 MiB file, 63/64 MiB owned-output, 175/180-second, 5 GiB reserve and shared-lock limits must remain unchanged. The new observer requires a separate binary pin even when linking the already qualified core archive. Existing 606 stores, 157 entries, all three RAM views and both frames must be compared against the qualified control before attributing any stack sample.

Each inferred stack frame must be validated against actual candidate prologue/epilogue instructions, stack adjustment, saved-register offsets, correct MIPS return address and delay-slot semantics. A static return address or plausible pointer is not an observed caller event, and unrelated stack contents must not become a guessed clock. The five final actor bytes not reproduced by the CPU-store stream remain unexplained. Independent game-update counter writer/storage, pause and speed behavior, STOP and a second actor remain open. No observer change, compilation or native run is authorized by this plan.

## Qualified bounded stack replay and static lead

One separately authorized replay at source `a8195304190a507f5f701203211992c329c8a88c` captured eight selected-entry stack windows, with two additional matching entries explicitly skipped and no cache/range failure. All three RAM views, both frames, 606 store events and 157 entry events matched the prior control byte-for-byte. The private manifest SHA-256 is `f3da1e3294b7ba8815081f415b9b33fdc380470fe44e568064319f8da4a47395`, stack stream SHA-256 `e21f56a9c90b73d982402e26eebbdbb08cfa02c8deee509eefaefb615a624239`, and owned output 60,689,701 bytes before the manifest. Private ROM, RAM, frame and stack data are not distributed.

At each entry the recorded RA was `ffffffff8013b418`. The saved word at SP+0x20 was `8013b500` in the first window and `8013ca74` in the remaining seven; the instruction at each saved RA minus eight is a JAL targeting `8013b3f8`. For the latter seven windows, further saved-RA hypotheses, checked against the local frame-size/save instructions and the corresponding JAL target words, form the candidate chain `80023990` → `801500cc` → `801505f4` → `8013b0b0` → `8013c800` → `8013b3f8` → the observed `8000c390` entry. These are stack-unwind hypotheses supported by static instructions and the captured stack, not independently observed entry events for every frame. The first window has a different intermediate path.

Static instructions near candidate caller `80023920` load the word at `800a5acc`, decrement and store it, reload 100 after the result reaches -1, and conditionally set a byte at `800a5ad0` when the result reaches zero. Across the three RAM views the word is 67, 50 and 31; the byte is zero in all three. Candidate `8013b0b0` reads that byte in the caller chain. This is a promising periodic countdown/flag hypothesis, not an authenticated independent game clock: the stack does not prove that the enclosing function runs exactly once per game update, and pause/speed behavior and the flag's full effects are untested. A local PC reference fork has a 100-frame tile-visibility countdown, but its revision is not the pinned OpenBW revision and its behavior does not identify the N64 field. Confirm the actual writer/caller dynamically and use independent pause, resume, speed and actor controls before any cadence claim. The five previously unexplained final record bytes remain unresolved.
