# Native actor snapshot differential and next experiment

This source-only analysis reuses the two private cache-aware Terran custom RDRAM samples documented in the [observer audit](../2026-11-07-n64-actor-observer/README.md). No emulator, new native capture, guest write or savestate manipulation was performed. The baseline screenshot showed a four-unit selection; the later screenshot showed a selected SCV near the right-hand mineral line. Other workers continued naturally gathering and the mineral HUD rose from 66 to 98, so sample differences are not uniquely attributable to the attempted Move. The asynchronous screenshots and two samples do not establish uninterrupted record identity, selection, STOP, writer PC or game-clock cadence.

The earlier broad heuristic found five stable candidate 60×256 big-endian 32-bit values; four are evenly spaced 312 bytes apart and the fifth lacks that stride and is unaligned. In the four same-process candidate neighborhoods, a repeated big-endian 16-bit pair at offsets +8/+10 relative to the putative HP word was (1936,3956), (2024,3845), (2048,3924), and (2004,3956) at the first sample; only the second pair changed at the later sample, to (2229,3841). The same candidate's pairs at +16/+18, +20/+22 and +32/+34 show the same change. These are plausible position-like values and the rightward change agrees directionally with the later screenshot; neither fact authenticates their meaning or the actor. All four had a stable byte 7 at +93 and stable byte 1 at +153, plausible type/owner-like fields but not proven. A byte at +135 changed from 0 to 64 in only the second candidate; its role as selection or another state bit is unknown. A byte at +76 fell in three neighborhoods and changed 0 to 7 in the second; its function as an order or timer is also unverified. Exact physical offsets and the full differential remain private process-specific hypotheses and must not be reused blindly after reset.

The [original StarCraft 64 manual](https://nintendo64.pl/wp-content/uploads/StarCraft-64-USA.pdf), printed pages 4 and 7, distinguishes A selection, R visible same-type group selection, the analog cursor, B contextual attack/move or mining, and the displayed C-button Move command. The captured SCV UI specifically labels C-Right as Move. Those pages do not identify a STOP shortcut; B must not be treated as STOP. Verify an actual displayed STOP command before claiming that intervention.

A next bounded *design*, not an executed test: use a newly qualified copy of the pinned frontend with three 8 MiB samples and at most three framebuffer captures. Include the 32 MiB isolated ROM copy, all logs, saves and metadata in a strict 64 MiB per-attempt output accounting; tighten stdout/stderr budgets and prove file-count and metadata bounds first. The existing N1 attempt produced 16 MiB of RAM samples; these proposed samples would add 24 MiB, for 40 MiB of known N1 snapshots, without inferring an unknown task-wide remainder. Hold the shared lock, verify at least 5 GiB free on the output volume, and preserve the 180-second and 14,000-step caps.

In fresh Terran custom play, visibly select individual SCV A and take a screenshot and baseline sample. Issue C-Right Move to a visibly distinct open destination, wait, then capture a second sample and screen. Independently select a different SCV B and order a different directional Move while A's state is observed, then capture a third sample and screen. Validate actor ownership, type, positions and actual selection within this process; distinguish incidental mining and reject ambiguous or reused records. Only attempt and label STOP after the on-screen UI identifies it. Repeat a fresh reset separately before treating offsets or transitions as stable. These snapshots cannot supply store writer PCs or prove a dispatch clock.

Only after actor identities and fields are independently corroborated should a separately reviewed copied-ares interpreter hook record bounded CPU stores within the fully validated actor spans and candidate clock spans, retaining PC, address, width, value and sequence without guest reads in the hook. DMA and cache-writeback identity changes remain separate blind spots. A candidate world-update PC must independently withstand pause, speed and fresh-reset interventions; VI, the old linked-list countdown and the sampled zero CPU thread clock are not substitutes. No cadence-based engine change follows from this two-snapshot analysis.

## Three-sample frontend budget proof before execution

The separate follow-up observer permits at most three 8 MiB RDRAM samples and three frames within the existing 2 MiB frame budget. The parent caps stdout at 256 KiB and stderr at 512 KiB. The child normally runs with a 2 MiB per-file soft limit and 8 MiB hard limit; only while synchronously writing a validated RAM snapshot does it raise the soft limit to 8 MiB and immediately lower it again. During that synchronous copy no guest CPU execution is requested. The fixed pinned USA ROM copy is 32 MiB. The pinned ares `mia/medium/nintendo-64.cpp` identifies StarCraft 64 as a 128 KiB Flash game; the isolated frontend connects no controller pak.

For this profile a deliberately conservative byte bound is: ROM 33,554,432; three RAM files 25,165,824; all frames 2,097,152; input CSV 2,097,152 (soft file cap); callback CSV 655,360 (16,384 rows × 40 bytes); command CSV 560,000 (at most 14,000 one-step commands × 40 bytes); status 132,352 (256 × 513 plus 1,024); stdout 262,144; stderr 524,288; expected cartridge Flash 131,072; and 1,048,576 reserved for manifest and miscellaneous metadata. Total 66,228,352 bytes, below 67,108,864 bytes by 880,512. The command/callback fields' maximum decimal widths are below those row allowances. This is a source/profile bound, not a claim about arbitrary ROMs, optional peripherals, unexpected upstream files or stalled filesystem operations; the wrapper additionally rejects recorded output above 63 MiB before writing its manifest. No task-wide remaining-budget claim follows. Fake range/cache-conflict tests, real per-file soft-limit toggling and wrapper admission/lifecycle tests must pass before launch; binary and pinned inputs must be requalified after the frontend change.

The isolated three-sample frontend built at source `eb601c56ea3ac6d614c3bd33ce189361e6aec92e`; its binary SHA-256 is `68b0130dacf1b9463e346402c7e438c51648353ee72d74ac57cbf71cef71829e`. The fake range/alias tests, per-file OS limit test, and existing wrapper lifecycle tests passed, and all 12 copied library/generated-resource hashes remained unchanged. This qualification used no game ROM or emulation; it does not claim any actor identity or native timing.

## Failed fresh follow-up

The one authorized fresh follow-up used the separately qualified three-sample binary and hardened pinned wrapper at source `14e2fb75bdd6889c9d2ce29c88966ee18caa733d`. The preplanned 5,597-step input file SHA-256 was `0dc63d6f4d75bea864c7c09d25c52146c9faad93890c7ca42c4443d04cfef230`. The wrapper reported READY, then the child terminated during its first 700-step command with return code −25 (`SIGXFSZ` on the host), after 1.201 seconds; it produced no frames or RAM snapshots. Checked inputs remained unchanged and recorded output totaled 33,554,481 bytes, including the isolated ROM copy. The wrapper SHA-256 was `9364d82773418f50485c36e36971b25842544c36d97e3c6c455cac69c38070c0`; the actual partial command file SHA-256 was `74c397e9edc9e191f521758fe2956a574253983db95d0491101bbb346e7b8d51`, and the outer run log SHA-256 was `7f27f54dbd4fc4062a28d8e9c059518c6d73b6b8e66f7804af0f1bb1ebfaa667`. The process did not reach the two actor selections; no identity, movement, STOP, timing, writer-PC or cadence observation follows.

The signal is consistent with the new file-size limit, but the write and file responsible were not observed, so the precise cause is unestablished. The source/profile arithmetic above is a proposed budget, not proof that this tightened observer can run successfully on the actual frontend. The process was not restarted, no additional RAM snapshot budget was consumed, and the failure records remain private. Any future work must identify and review the limit interaction before another authorized attempt, without silently relaxing the 64 MiB per-attempt cap.

A subsequent read-only file inventory found 33,557,369 bytes in the attempt directory including the 2,888-byte manifest; the earlier recorded figure was taken before the manifest was written. The directory contains no 2 MiB file. The failure occurred during `root->run()` before the observer was asked to capture RAM. The pinned Vulkan source has a conditional pipeline-cache write, but neither its activation nor a corresponding file was established, so it does not identify the writer. A bounded search of the user's Library cache and `.cache` to depth five found no 2 MiB file modified within two minutes of the attempt; the temporary-directory search was interrupted and is incomplete. These checks cannot exclude other paths, deleted files, or earlier timestamps. The wrapper's output counter covers its output directory, not external caches or the outer run log; therefore neither that count nor the proposed arithmetic proves a complete host-wide output total.

The copied pinned ares build does not enable the previously considered Granite pipeline-cache writer: its saved compiler flags omit `GRANITE_VULKAN_SYSTEM_HANDLES`, which gates that code. The frontend directly constructs its Vulkan context without assigning a filesystem handle; that handle defaults to null. Thus the source does not resolve a `cache://pipeline_cache.bin` path in this build. This excludes that specific candidate, not writes by MoltenVK or the OS. The ≥2 MiB output-directory file is the unchanged ROM copy, loaded into in-memory VFS before READY; a scoped, name-based search of Library/Caches and .cache found no identifying shader/pipeline cache, but is not a complete host-wide inventory. The signal's writer and path remain unknown.

A later source-only diagnostic prototype installs a Darwin arm64 `SIGXFSZ` handler after opening a fresh private record file. It uses a fixed 40-byte positional write and `_exit` without raising limits or resuming the guest. Its SDK `ucontext` register accessors record host PC, LR, and SP, not a guest writer PC; a host address may be inside libc or a driver, and neither identifies the file descriptor or path. Address signing and ASLR limit later attribution. The wrapper accounts for and hashes the record as metadata, and is deliberately disabled until the changed observer binary is separately built, qualified, and pinned. The historical run used the earlier binary and wrapper; this diagnostic was not present then. A synthetic asset-free test is the only authorized execution of this prototype this turn.

The first synthetic diagnostic compile failed because this Xcode SDK rejects `<ucontext.h>` without `_XOPEN_SOURCE`, and strict warnings rejected the original initializer. The source now uses `<sys/ucontext.h>` and C++ zero initialization. An asset-free fake child subsequently passed under the shared lock and 5 GiB reserve: exceeding the 2 MiB soft file limit yielded one 40-byte signal record with nonzero host PC and SP and exited with 128 + SIGXFSZ. This tests the fixture only; the full observer binary remains unbuilt and unqualified, and the wrapper remains disabled.
