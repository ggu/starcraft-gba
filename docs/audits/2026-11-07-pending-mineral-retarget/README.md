# Pending mineral-trip depletion

An explicitly ordered, empty worker could still be traveling to a mineral field when another worker exhausted it. In the shared cargo path, the pending-trip validity check then made the worker idle before the established-depletion continuation logic ran. This affects the Protoss10 custom path and other products using the shared cargo capability.

The update checks only an empty worker with a pending mineral order and a valid, now-depleted target. It reuses `worker_continue_minerals`, which searches the former cluster within 192 runtime pixels, requires human-visible or previously explored resources, and rejects unreachable candidates. A successful replacement retains the explicit pending order. If no candidate qualifies, the existing cancellation path applies. Invalid targets, non-mineral orders and workers carrying resources keep their previous handling; STOP remains authoritative. This is bounded continuation, not proof of native resource-allocation parity.

At source `62a5f5f4`, the actual P10-vector ASan/UBSan fixture uses the real selection/interact dispatcher and worker updates. One selected Probe is ordered toward a field while a second Probe gathers its final eight minerals; the first then targets a nearby available field. It also checks STOP, a hidden replacement and a visible replacement while carrying gas. The included existing gather fixture continues to exercise unknown and mixed cargo. The same fixture at `68ca2d71` failed at the intended pending-retarget assertion, and the candidate passed; the earlier fixture-setup failure is also retained. These are authored HOST scenes, not ordinary-play or N64 timing evidence. All 589 copied inputs remained hash-identical before and after the focused run.
