# Pinned ares software-rendering feasibility

Read-only source inspection of pinned ares v148 commit `0aafd85789215e84e1e43415c07d4c88461b7899` found no usable software RDP for a native visual reference in the current build. `ares/n64/system/system.cpp:27` sets `vulkan.enable` from the `Enable GPU acceleration` option; `ares/n64/rdp/render.cpp:47–55` then bypasses Vulkan and enters the non-Vulkan command dispatcher. However, that source's triangle, textured rectangle, fill rectangle, texture-load and color-image rendering methods are empty stubs (`render.cpp:565–707`). `SyncFull` can still raise the DP interrupt, and `ares/n64/vi/vi.cpp:175–225` can scan RDRAM into a video buffer, but this is not a software rasterizer or proof of rendered game graphics.

The copied build uses `PROFILE_PERFORMANCE` and `VULKAN`; the RDP fallback above is not made into a software renderer by those flags. The observer currently selects GPU acceleration, requires the Vulkan-enabled status, and treats `No RDP rendering support` as failure. Disabling GPU while weakening these checks could continue CPU/controller execution but would silently produce incomplete rendering, unsuitable for a fog, death, or gameplay visual comparison. No claim is made about exact timing, performance or CPU behavior under that unsupported configuration.

No code, ROM, emulator state or private asset was changed, and no native or software-renderer test was run. The previously observed read/write Metal cache descriptor larger than the existing file limit remains a candidate, not proof of the failing syscall. A separate genuine renderer or an independently reviewed approach to cache behavior is required before pursuing a visual reference; do not relax the existing limits or label the empty RDP methods as software rendering.
