# Periodic countdown: bounded pause/resume attempt

This is a proposed single replay, not a pause, resume or clock observation. The original [StarCraft 64 manual](https://nintendo64.pl/wp-content/uploads/StarCraft-64-USA.pdf), printed page 4, identifies Start as Pause. The earlier [native audit](../2026-11-04-n64-parity/README.md) describes a pause menu with a Resume option; neither source establishes that a second Start dismisses this particular custom-game menu. The proposed second Start is a testable input hypothesis, and a retained frame must visibly show play resumed before any resumed-state claim. A pause menu alone does not independently prove that every game subsystem is stopped.

The separate wrapper retains qualified binary `995b8b329ae703597c820607571b62df74a6a0048405b90c12765be53e8903bf` and pins plan `98a0da0f196270ca95ef786c89dfeb870c7fb7a3a69392fe407ebc5e953a1d2a`. All button/axis/count commands through completed step 4,322 match the earlier controlled Probe replay; only the original capture markers at 4,260, 4,321 and 4,322 are suppressed. The authenticated baseline RAM view remains at completed 4,201 and the selected-Probe play frame at observed 4,258.

The appended sequence is: Start mask 2 for 10 steps, neutral 20, paused-settled RAM view at completed 4,353, neutral 60, second RAM view at completed 4,414, pause-frame request at observed 4,414, Start mask 2 for 10, neutral 20, and final resumed-play frame request at observed 4,445. Total is 4,446 frontend steps. The final frame must be the last command because the qualified frontend stops at three copied frames. The second Start may not resume; if the pause or resumed-play image is not visibly established, preserve the attempt as incomplete and make no pause/resume conclusion.

The testable prediction is no watched countdown writes between the two paused RAM boundaries and identical watched bytes there, then one or more validated countdown stores after the resume input while the final frame visibly shows play. A different result is evidence against that prediction, not permission to relabel the countdown a clock. Event steps reflect callback execution boundaries, not authenticated game frames. First-view SHA-256, original controller prefix and pre-pause actor/counter event prefix should be compared with the earlier control; removal of intermediate captures can affect asynchronous observation, so any nonmatch remains a finding rather than a false parity claim.

The existing three 8 MiB RAM, three 614,400-byte frame, ≤96 counter, ≤4,096 actor-store, ≤1,024 entry and eight stack-record limits remain unchanged, as do 8 MiB Metal-compatible per-file, 63/64 MiB owned-output, 175/180-second, 5 GiB and shared-lock guards. Counter or entry overflow fails the process; stack truncation must remain explicitly reported. The maximum ROM + RAM + three frames is 60,563,456 bytes before event streams and metadata, leaving 5,497,832 bytes below the 63 MiB pre-manifest threshold. This arithmetic is not a wall-time guarantee: the longer interpreter continuation may hit the deadline. A first fake prefix test incorrectly specified one changed marker index; it was corrected, and all four wrapper tests passed. No emulator or native build was run for this plan. A real run requires source/plan review and separate authorization; speed scaling, STOP, a second actor and an independent game clock remain open.
