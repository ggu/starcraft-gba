# Bounded N64 CPU store observation: source design

This is a proposal based on pinned ares `0aafd85789215e84e1e43415c07d4c88461b7899`, not a built hook, a native run or writer-PC evidence. The preceding selected Probe candidate and process-local physical range are described in the controlled-Probe audit. The selected actor address must be authenticated again in any new run; a fixed address alone is not a general actor identity.

The existing CPU instruction tracer calls `CPU::Debugger::instruction` from `CPU::instructionPrologue` (`ares/n64/cpu/cpu.cpp:168–176`). When enabled it checks an address filter and formats a disassembly (`cpu/debugger.cpp:1–36`); it is an instruction tracer rather than a non-stopping committed-store callback. `CPU::write(PhysAccess,u64)` reports the raw virtual address and size to `GDB::server.reportMemWrite` before the cache or bus write (`cpu/memory.cpp:187–193`). The GDB server uses this for watchpoints and stops the guest (`nall/nall/gdb/server.cpp:50–82`); its documentation says value is fetched by the client, so this API does not directly provide an observational post-store event. The debugger write path is separate and must not be used to manipulate guest memory.

A separately copied and explicitly instrumented ares core could instead capture the fetched guest PC and opcode in a small host-only instruction context immediately around the interpreter's `decoderEXECUTE` call (`cpu/cpu.cpp:164–171`), then call a bounded host sink only after `CPU::write(PhysAccess,u64)` has performed the cache or uncached write. Filter using the successfully translated physical address and width, require overlap with a fixed authenticated RDRAM-only range, and never perform a second guest read, invoke MMIO, alter data, PC, registers, exceptions or timing configuration. Log the original virtual address, translated physical address, width, written data, captured instruction PC/opcode, decoded base-register index and its pre-instruction value, plus monotonic event sequence and frontend step. Use a bounded preallocated ring: at most 4,096 fixed records, with header and total serialization at most 256 KiB; overflow is explicit and disqualifies completeness. Do not infer guest frame or independent game time from event sequence or `cpu.clock`.

Correctness requires proving the instruction context really belongs to each store and survives branch delay, exception and synchronization paths. The interpreter uses `pipeline.begin()` before prologue and `pipeline.end()` after execution; store context must use the prologue's actual PC/opcode rather than a later capture-boundary PC. Confirm effective base-register extraction from the real opcode, signed displacement, address translation and cache/direct behavior with fixtures. Unaligned instructions can issue multiple component writes and may fail partway (`cpu/interpreter-ipu.cpp:692–838`); retain component order and do not label an incomplete instruction atomic. SC/SCD writes are conditional (`:673–689`). Record only writes reached through the selected interpreter CPU path; DMA, other processors, direct core mutations and uninstrumented recompiler paths are outside coverage. The existing authentic transition must prove CPU and RSP recompilers off before arming. Store instrumentation cannot turn the saved CPU thread clock into an independent clock.

Before any native attempt, review the isolated source diff and compile it against separately copied pinned core sources and libraries; never mutate the pinned checkout or existing build. Asset-free tests must cover overlap boundaries, cached/direct translations, rejection of non-RDRAM and failed writes, byte/half/word/double widths, sign-extended base addresses and offsets, branch-delay PC/opcode attribution, conditional SC failure, unaligned multi-write order, event cap/overflow, output bounds and unchanged guest-visible write results. A real qualified attempt would retain the existing 4,322-step controller plan, three 8 MiB RAM views, two frames, 8 MiB per-file limit, 63/64 MiB owned output, 175/180-second wall bounds, 5 GiB reserve and shared lock. Its trace allocation must fit inside those bounds, and its RAM/frame results must be compared with the prior controlled replay. Run only with separate source/build/budget review and explicit authorization; no new emulator or core build occurred in this audit.
