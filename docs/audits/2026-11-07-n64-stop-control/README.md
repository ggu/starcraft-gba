# N64 selected-Probe STOP control: admissibility

The original [StarCraft 64 manual](https://nintendo64.pl/wp-content/uploads/StarCraft-64-USA.pdf), printed pages 4–5 and 7, says that B directs selected units to attack or move to the cursor and that the contextual C-button commands appear on screen. It describes issuing Move but does not identify a STOP shortcut. The retained qualified selected-Probe image from the pause/resume control visibly offers BUILD, MOVE, BUILDADV and ATTACK; it does not show STOP. Therefore neither B nor any particular C button is established as STOP for this selected Probe. PC Stop behavior is not an N64 control mapping. No STOP command file is admitted on that basis.

The previously qualified observer can trace this one selected Probe's 312-byte watched record, instruction-entry arguments, position/order stores and the separate periodic countdown. Its existing ordinary-input prefix authenticates the first RAM view at step 4,201, selects the Probe, and issues the previously observed Move. A future controlled test should retain that prefix and one frame identifying the selected moving Probe; take a second RAM view during motion; issue a separately verified ordinary STOP gesture while the same actor remains selected; then take a third RAM view and a final frame after a bounded settling interval. Compare the watched order/target stores and the post-settling position stream with the moving interval and retained record identity. A cessation at a natural destination, a different selected actor, an unverified menu label or an absent writer is inconclusive. A frame alone cannot prove movement ceased, and the periodic countdown is not a game clock.

The applicable limit remains three 8 MiB cache-aware RAM views, at most three 614,400-byte frames, 63/64 MiB owned output, 8 MiB Metal-compatible per-file limit, 175/180-second execution deadlines, 5 GiB reserve and the shared native lock. The established fixed event buffers and their overflow failures also remain in force; additional continuation can exhaust them, so the previous run's margin is not a guarantee. The first-view hash, input prefix, observer binary and source must be pinned and verified, and the proposed exact steps, capture markers and event-budget admission tested and reviewed before a native attempt. No guest-memory injection, external state or CPU rebuild is needed in the proposed observation. It remains an authentic same-process hybrid restore, not a fresh-interpreter or hardware timing claim.

The next prerequisite is a primary N64 control source or a retained native interface view that actually identifies how this Probe can receive STOP. If the gesture requires a button unsupported by the existing observer, source-backed input support, tests and a separately pinned build are required first. No STOP, speed, independent game-clock or second-actor conclusion is claimed here; no new emulator run was made for this audit.

The prior run used the ordinary `select2` scenario in `experiments/ares-headless/main.cpp`, and completed successfully; its original frontend and asynchronous callback observations are distinct from the later JIT-only observer.

The source-only candidate `tests/sc64-ares-observer/fixtures/native-marine-stop-ui.txt` has SHA-256 `395b4ad0f55b12fc5a6761813051813ecf282b4ee37d9749425804bc4ded0dee` and 7,142 steps. It reproduces the original `select2` button/axis intervals through selection, requests a frame at step 7,090, presses C-Down (mask 256) for steps 7,100–7,109, then requests a final frame at 7,141. The manual's contextual-command rule and retained Marine label justify testing this particular button; a changed frontend, timing or selection can produce a different result. Require the first frame visibly to show the selected Marine and STOP label; the final image must be inspected, and an idle Marine pressing STOP is only UI/control exploration, not proof of moving-to-stopped behavior. There is no pretense that a two-frame image proves an order write or that this Marine shares the prior Probe's watched address.

A future reviewed wrapper for the already qualified visual-only JIT binary may admit this exact pinned schedule, with no RAM snapshots, at most two 614,400-byte frames and unchanged 8 MiB Metal-compatible per-file, 63/64 MiB owned-output, 175/180-second, 5 GiB and shared-lock guards. The raw ROM plus two frames is 34,783,232 bytes before logs and metadata; this is not a wall-time guarantee. The present fixture is preparation only: no wrapper admission, new build or emulator run has been performed. A later moving-unit order/position experiment needs its own identified actor, watched range and independently reviewed instrumentation, and must not reuse the Probe address for the Marine.

## Proposed Marine Move then STOP exploration

The separate candidate `tests/sc64-ares-observer/fixtures/native-marine-move-stop-ui.txt` (SHA-256 `10234dbf1017e0dd2af5d53929c4924558f742fc0b7dcbe8fc2890a582ed0a93`) keeps the same T1 selection prefix and first frame at observed step 7,090. It then moves the cursor right using X=24000 for steps 7,100–7,139, presses the displayed C-Right MOVE (mask 64) at 7,140–7,149, requests a second frame at 7,169, presses the displayed C-Down STOP (mask 256) at 7,170–7,179, and requests a final frame at 7,230; total 7,231 steps. The manual describes the C-button Move-to-cursor gesture, while the retained Marine frame identifies both labels. Actual cursor travel, selected Marine, destination, movement and input interpretation remain hypotheses to check: this different frontend has not replayed the schedule. A first frame without the Marine and labels, an intermediate frame without visible displacement toward a still-distant destination, a final frame obscured or a completed/blocked path leaves the result inconclusive. Even successful images alone do not distinguish STOP from arriving or obstruction.

This visual candidate is not an N1 writer-correlation test. The qualified counter observer's watched address and authenticated 4,201-step baseline belong to the earlier Protoss custom Probe, not this T1 Marine. For a later trace, independently authenticate the selected Marine record and its ownership, HP, type and positions from a bounded baseline and visible selection; validate a long, unobstructed target and motion before intervention. Then an isolated observer role, linked to the existing qualified CPU archive without changing the CPU core, must arm only after validating that exact Marine baseline and watch only its validated record; preserve cache-conflict rejection and bounded event overflow failures. Capture actual order/target and position writes before and after C-Down, compare settling and a separately controlled no-STOP movement continuation, and reject natural arrival/obstruction or selection changes as alternative explanations. A new observer source, baseline hash, binary pin, explicit event budget and separate reviewed protocol are prerequisites; no universal actor ABI or game-clock claim follows. No native replay is authorized or claimed by this plan.
