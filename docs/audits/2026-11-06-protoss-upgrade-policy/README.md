# Protoss upgrade policy and job admission audit

This is a read-only audit of main `21bc709b` and experimental research foundation PR #318 (`321de842`). The foundation stores completed levels only; it is default-off and does not implement paid jobs, scenario permissions or upgrade gameplay. No runtime behavior is added here.

## Producer and persistence plan

Forge raw type 166 and Cybernetics Core raw type 164 are candidate producer identities. A bounded job representation can use an authenticated completed producer's existing `level` for family-plus-one and `queue_progress` for paid remaining time; `queue_count` must be zero and the slot itself binds the job. `game.c:1200–1207` defines these fields in the full record; `sc64_zp_building_types.h:10–18` uses narrow `u8 level` and `u16 queue_progress`, sufficient for the currently quoted 1–6 kinds and at most 6200 policy ticks. `sc64_race_save_types.h:128–139` selects typed, derived, packed, or s16 rows; typed/packed codecs retain these fields (`sc64_p7_typed_building_save.h:90–98`, `sc64_compact_building_save.h:91–114`). Existing save validation checks queue and field bounds (`race_save_adapter.h:2924–2925`) but does not authenticate new job meanings. Other building types already alias these fields for battery, flying facilities and BC research, so restrict interpretation to authenticated Forge/Core, a new journal tag, and valid mutually exclusive normal profile layouts. Prove producer type has no competing production/service aliases on each profile; never reinterpret old values as new jobs. The separate older unwired `sc64_protoss_research_jobs.h` prototype at `63dedd14` accepts `int *` kind and remaining fields, which cannot bind directly to compact `u8`/`u16` fields. PR #318 instead defines `sc64_pr_begin` with a `uint16_t *remaining`; it has no producer-bound job adapter. For either approach, use checked local snapshots and a typed atomic commit, not pointer casts.

Use one shared adapter, not a mission predicate: custom owner key is the authenticated compact owner; campaign key is the raw source slot, verified against the active or candidate mission binding. `sc64_protoss_services.h:92–121` provides binding-specific source-owner resolution and `RACE_PROTOSS_SLOT`; `sc64_p7_runtime_adapter.h:44–53` explicitly allows multiple source slots to collapse to ENEMY. Validate both direction and mode/mission with candidate-specific binding during load. Do not infer a source slot from compact owner, and do not assume `race_owner_minerals/gas` (`race_adapter.h:71–94`) distinguish source wallets. Authentic production, construction, rescue, transfer and capture paths must retain or explicitly update provenance; reject or suspend unsupported ambiguous paths rather than awarding another source owner's research.

For each live or detached candidate, scan at most `MAX_BUILDINGS` and reject malformed kinds, invalid duration, dead/incomplete/wrong producer, nonempty queue, bad owner binding, disallowed source max/initial level, and duplicate owner/family jobs before publication. Charge exact current-level prices atomically only after completed/powered producer, prerequisites, wallet, uniqueness and permission checks. Advance only with a verified owner and power; define power loss as pause only after the PC-source policy is reviewed against N64. On completion clear the producer job and increment only its authenticated owner's family. The existing foundation's 12-byte completed-level payload and new tag do not by themselves persist active jobs or authenticate their aliases. Integrate active job validation into both detached load preflight and writer before journal commit; preserve fallback and byte/RAM/stack guards for every normal race profile.

Pinned OpenBW `bwgame.h:3501–3535` refunds full cost on cancel and three quarters on producer destruction; this is PC behavior, not an N64 observation. Adapter transitions need one atomic cleanup/refund to the original authenticated payer on cancel, death, transfer/capture, and slot reuse. The existing BC lab example at `race_adapter.h:566–603` cancels before transfer and refunds on destruction, but does not prove source-owner wallet correctness for these Protoss jobs. Confirm capture/ownership behavior and map wallet policy before shipping. Reset levels and jobs at new-match boundaries; load must preserve them. Legacy generic SIDE-only levels and pending jobs must not silently turn into one typed family: preserve both ground/air effects and old pending payment/timer or define an explicit reviewed compatibility policy without inventing shields. Existing experimental helper does not implement this migration.

Finally wire source-identified upgrade families into weapon/armor/shield/range calculations and special paths, not inferred flight or attack target. The source facts tool at `tools/sc64_protoss_research_facts.py` in the separate facts branch authenticates unit/weapon tables; a stock-table generator must carry these numeric IDs into all runtime routes. Scenario cap/initial state, typed jobs, owner banks, combat and UI need cross-profile ordinary-input and save/load tests before promotion. The 5:4 simulation conversion is an existing approximation, not verified N64 duration.
