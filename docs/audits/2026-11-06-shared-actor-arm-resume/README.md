Generated inputs were recovered privately from the prepared `shorts-z2` workspace; the selected input hashes and full commands/output remain in the isolated checkout's ignored `.local/armq-logs/`. The corresponding `armq-z7` compile reached link but failed the unchanged IWRAM assertion: `__iwram_end=0x030052b8`, 696 bytes beyond its limit. Its `__bss_end=0x0203d4b4` passed the EWRAM assertion. An otherwise identical Z7 derived-save build with `ARMQ_STAGE=` and `ARMQ_PROFILE=` linked at IWRAM end `0x03004f68` and BSS end `0x0203d4ac`. This is a stage-off comparison, not the full staged candidate. Symbol comparison of a diagnostic unqualified ELF found increases in `update_orders` (464 bytes), `unit_step_clear` (148), bucket begin (64), bucket move (48), contact check (32), and target-index move (24), plus smaller changes and veneers. These are hot paths; no placement change is qualified by this comparison. The diagnostic ELF was linked with `--noinhibit-exec` for analysis and is not a valid build.

Compiler `.su` reports are per-function static estimates, not runtime high-water measurements or whole-call-chain bounds. The largest reported frames include Terran `race_save_game` 2,488 bytes, `race_load_game` 2,328 bytes, and `race_load_preflight_candidate` 1,520 bytes; Z7 candidate `race_z7_save_candidate_valid_for` 3,240 bytes and `race_z6_save_candidate_valid_for` 3,192 bytes. They cannot establish total stack use without call-chain and runtime qualification.
