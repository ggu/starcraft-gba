# N64 selected-Probe writer: caller and clock candidates

This static analysis uses only the three private RAM views and 606-event store stream from the [bounded selected-Probe run](../2026-11-07-n64-store-observer-design/README.md). No new emulator execution, guest write or core build was performed. The source-backed actor record and writer observations remain specific to that hybrid run; frontend run counts are not game-update counts.

At the position-shaped writer PCs `ffffffff8000c434`/`438`, nearby MIPS words are consistent with halfword stores from registers to offsets 0x28/0x2a of the actor base. A nearby stack-frame prologue occurs at `8000c390`. A bounded aligned RAM search found JAL-shaped words targeting that address at `8000c548` and `8013b410`; the latter is immediately preceded by a plausible prologue at `8013b3f8`. The order-shaped store at `ffffffff80122908` is inside a short MIPS sequence beginning at `80122904`, followed by stores to the target-shaped fields and return. JAL-shaped words target that entry from `80008b10` and `80139b28`. These are candidate call sites in sampled RAM, not observed call events, verified function boundaries or evidence that either caller ran during the selected Probe's update. Indirect calls, dynamically loaded code and data that resembles instructions limit the static search.

One candidate caller reads several nearby halfwords using addresses in the `800a3420` area, but static proximity to a position writer is not sufficient to call those values a game clock. An intentionally narrow scan for four adjacent MIPS instructions constituting an absolute KSEG load, increment by one and store found one candidate at `800bb040`; it was zero in all three views. This search neither identifies a game-update counter nor rules out different instruction scheduling, non-adjacent instructions, register-relative addressing, other counter widths or clock storage. No candidate was selected merely because its value changed. The five final record bytes not reconstructed by the CPU-write stream remain unexplained and do not establish a clock or hook completeness.

A useful next isolated observer should record only execution entry events for the small candidate entry/call-site set above, together with the already bounded actor stores. Capture actual entry PC, decoded opcode, guest return address and a bounded sequence index; verify instruction bytes and branch-delay attribution before interpreting call relationships. A sequence index orders observed events only. Reusing the same input and retaining the three-view/two-frame, event/output, 175/180-second, 5 GiB and shared-lock caps would permit comparison to the already verified baseline. Exact predictions: if `8013b410` is the active direct caller of `8000c390`, an observed entry of the latter should have guest return address `8013b418` (including ordinary MIPS JAL delay-slot semantics); similarly `8000c548` predicts return `8000c550`. If neither is observed, do not assign a caller. An order-writer entry at `80122904` reached by `80008b10` or `80139b28` should respectively carry return `80008b18` or `80139b30`. Nested calls, delay slots, exceptions and instruction boundaries need explicit fixtures; no inferred entry event may be substituted for an actual one.

Once a genuine update-loop candidate is observed, a separately planned ordinary-input pause/resume control should compare candidate entries and any independently sourced counter before pause, during a visibly confirmed pause and after resume. A real game-update counter hypothesis must identify its writer and storage independently and predict stable paused values plus consistent advancing updates; use an independently controlled second actor and a fresh reset to reject a per-unit or presentation timer. Speed-change behavior and STOP must be learned from actual native UI/manual evidence before attempting them. Three RAM samples and two frames cannot by themselves prove all of these interventions in one run; split future experiments into reviewed bounded attempts rather than infer missing states. No new trace, core compilation or native run is authorized by this document.

## Spatial scratch is not a clock candidate

A later read-only disassembly check narrows the four halfwords near `800a3420`: the observed position-writer function compares actor offsets 0x28/0x2a to halfwords at `800a3426`/`800a3424`, copies prior coordinates to `800a3422`/`800a3420`, and writes the new coordinates back to the actor. Its caller subtracts the corresponding pairs and shifts by five before conditionally setting a byte. Their three-view values are respectively 160/319/100, 1056/1052/1059, 164/320/103 and 1060/1051/1062. This supports temporary spatial state rather than a monotonically advancing game counter. A byte at `800e009f` is copied to actor offset 0x20 and has values 72/64/72; its exact native meaning is unproven, and it likewise is not a monotonic counter in these samples.

The local pinned GPTP PC reference (`ce321f0fa83174aee741b91f1b2eaec30300773e`, `GPTP/SCBW/scbwdata.h:113`) identifies an elapsed-frame value in its PC address space. That reference supports the existence of a PC game-frame concept, but its PC address is not an N64 mapping. No corresponding N64 global storage or writer has been authenticated. Further tracing should follow the executed caller path and require writer, pause/resume and independent-actor evidence rather than treating the spatial scratch or a changing value alone as a clock.
