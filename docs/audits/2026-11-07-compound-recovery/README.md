# Proposed compound Flash recovery contract

This is a design, not an implemented or qualified recovery format. The normal game remains unchanged. The experimental compound 0x4a envelope would advance to version 3, and its writer would reserve a fixed ownership marker in the isolated commit sector after the four-byte commit tag. Existing committed version-1/version-2/unknown records, including records with bad checksums, are not rewritten, re-tagged or erased by this writer. The original 32 KiB remains read-only and must be blank for this stage. The previously produced markerless version-2 interrupted records cannot safely be attributed and remain fail-closed.

The reserved marker is an explicit format-ownership contract, not a cryptographic signature. Committed foreign records take precedence over any apparent marker: a matching committed tag/metadata with an unsupported or unidentifiable envelope is refused even if its checksum is bad. Unknown uncommitted content that imitates the exact reserved marker cannot be distinguished from an interrupted owner write; such a writer violates the reserved marker contract. The protocol assumes exclusive transaction access, unchanged read results during one reselect/write operation, and a backend that refuses further mutation after an uncertain timeout.

On a fresh all-erased target, or after selecting an alternate target that is proven to be a fully checksum-validated, semantically valid version-3 record, first erase its isolated commit sector and verify every byte is erased. The previous selected winner and all data sectors remain untouched through that verification. Then program a fixed marker in a prescribed byte order, verify the complete marker, and only then erase/program the seven data sectors. Write the version-3 header, real base and bounded sidecars, metadata and payload checksum; verify them before programming the commit tag last. Programming order must be implemented in a separately audited writer; this design does not assume a multi-byte Flash program is atomic.

A marker-torn write on a previously blank target may be resumed only if the tag is erased, the marker is a possible bitwise partial prefix of the specified single-byte programming order, every other commit-sector byte is erased, and the entire data area is erased. A torn marker with old data present needs a separate proof: the surviving data/metadata must form the exact supported version-3 tuple, pass the full payload checksum and semantic validation, and be bound to the same slot. In either case complete and verify the marker without erasing the commit sector. An intact marker with erased tag authorizes re-erasing the data sectors and restarting the write; this retry does not erase the marker sector. Partial tag programming requires a commit-sector erase before retry, but only when the fully written data/metadata still pass the same version-3 ownership proof. An interruption during that erase is recoverable only while the surviving data/metadata provide that proof; otherwise fail closed. A fully committed supported record uses the ordinary selector and is not treated as an incomplete transaction.

The writer must reselect the actual admissible winner and check its full descriptor/checksum before any mutation, never select the current winner as the target, and recheck foreign ownership before the first target erase. A fresh reader must still select the earlier valid winner across every cut. No malformed record, read failure, stale selection, timeout or failed write may publish live actors, controllers, payers, debts, research, shots or wallets. The marker protocol does not establish authenticity against a deliberately forged device image, nor hardware erase geometry or timing.

Before claiming recovery, exercise the actual game producer, injected cut, fresh-process reader, retry save and fresh reload with complete selected-state comparisons. Independently enumerate cuts during every marker byte, isolated-sector erase, data-sector erase, header/base/tail/metadata program, tag program and read/verify operation; include partial bit erasures/programs, two existing slots, sequence wrap, bad-checksum foreign committed records, v1/v2 and unknown tuples, and preservation of the other winner and legacy region. If a cut cannot be classified without weakening these rules, retain an explicit fail-closed recovery gate. HOST model success alone is not ARM or physical-hardware proof.
