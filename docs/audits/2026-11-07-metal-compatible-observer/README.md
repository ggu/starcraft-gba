# Optional Metal-compatible observer file limit

A prior stopped-child snapshot showed an open read/write Apple Metal cache data file already 2,424,832 bytes, above the original 2 MiB process-wide soft file limit. The snapshot does not prove it caused SIGXFSZ. Pinned ares does not have a usable software RDP fallback. This candidate keeps the original strict mode (soft 2 MiB, hard 8 MiB) and adds only an explicit `--file-limit-mode metal-compatible` (soft 8 MiB, unchanged hard 8 MiB). There is no arbitrary limit parameter or cache environment override. This is a deliberate change to a process-wide limit, not a claim that external cache output is accounted for by the owned-output ledger.

The observer validates its initial soft/hard pair and restores the selected initial soft limit after each bounded RAM write. Its input CSV now has an explicit 2 MiB bound, previously enforced by the process soft limit. Existing maximums remain three 8 MiB RAM samples, 2 MiB aggregate frames, 67,596-byte image inventory, 64 KiB descriptor inspection, bounded status/callback/command logs, 175-second child and 180-second parent, ≥5 GiB free and the 64 MiB owned-output budget. The manifest identifies the selected mode, exact process limits and owned-output caps; no host-wide output census is claimed.

Asset-free limit-mode, snapshot restore, stopped-child, packed inventory and wrapper tests passed with the copied upstream input hashes unchanged. A later actual-child wrapper test confirms that strict and Metal-compatible launches inherit the intended 2/8 and 8/8 MiB pairs. Its initial `/dev/null` selector fixture failed on this host and was corrected to use a pollable pipe; both receipts are retained privately. No emulator or GPU probe was run for this candidate. The renderer, SIGSTOP inspection and limits require source review and separately authorized bounded native testing before any gameplay claim.
