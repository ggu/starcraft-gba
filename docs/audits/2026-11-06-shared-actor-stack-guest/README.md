# Staged Z7 system-stack paint and SRAM probes

This nonshipping ARM experiment uses the rare-actor dispatch plus diamond-placement candidate at source `9d87a539`, published as `74d0bad0`. It does not qualify all stack paths, the IRQ stack, campaign persistence or physical hardware. The experimental painter and physical scripts are in `tests/sc64-stack-qualification`; they never change gameplay world state or fabricate SRAM.

The uninstrumented Z7 candidate ELF SHA-256 is `f92afc50e43f63f4b93207886cc06458ca2bb7a1c68885c08dde3a4fe967aff2`, ROM `b54cb31ccfb6a2cbc80f60fc081663c8fee0d4beed8157ac2de5380da5497ae0`. The diagnostic ELF is `5ab9426f4312dcb3b8f4a63e5eac856815878cc6018dda60a8bc5de8adedc66e`, ROM `b0ff6f3d7766f3cefbba1d826c310a949b7930c36ea3872fb718aecf61474e6e`. Compiler command comparison found the same source order, include order and feature defines, with only `SC64_ARM_STACK_PAINT_QUALIFICATION` added. Both use the original linker assertions. The diagnostic ended at IWRAM `0x03004f10` and EWRAM `0x0203d4c4`; 1,565 copied private header/blob hashes matched the retained candidate checkout inputs at copy time and were unchanged across the diagnostic build; no earlier complete build-time manifest was available for this comparison.

Disassembly shows `main` reserves 56 bytes before calling a zero-frame painter before `gba_init`. The painter samples the actual SP, checks that IME is zero and SP is in range, then writes `[0x03005000, SP-512)`; it does not touch the IRQ/BIOS band. Observed SP was `0x03007dc8`, paint end `0x03007bc8`, and painted length 11,208 bytes. No claim covers startup before paint, the unpainted top 512 bytes and caller frame, the banked IRQ stack, BIOS behavior, an unexecuted path, allocations that do not write, or a write that restores the marker. An IRQ descending into the painted interval cannot be distinguished from a main-stack write. A positive marker is not a whole-program bound.

## Ordinary custom SRAM continuation

The source-pinned mGBA 0.10.5 backend used commit `26b7884bc25a5933960f3cdcd98bac1ae14d42e2` and `tools/sc64_headless_replay.c` SHA-256 `ad37a62dd47112481a0efc52dfca56a681b09005914c7296234c8416498a1530`; the built physical runner was `4199fe903b18c77e0833db1860c4968509cfc82e506bc6f2f9be7582b720fae2`. Both candidate and painter were run under the shared native lock and 4 GiB disk guard. Physical buttons chose map 1, Zerg human and one Protoss AI, advanced 600 updates, saved via START/B, and loaded its exported 32 KiB SRAM in a fresh process with HOME-L. Each continued for 120 updates.

Both runs passed the continuation tool's scoped save, load, lobby, frame, entity and resource checks. Their 30 recorded physical step calls, saved/reference/restored/resumed summaries and SRAM bytes matched; SRAM SHA-256 was `9085695f9749b077baffebe8c46b4dbae7c3152ba6322b356c6489b24db1ddee`. The system-region paint had 10,020 bytes untouched at save and continuation, and 9,740 at fresh load and continuation. The fingerprint does not cover all state or all effects. The test does not prove arbitrary saves, late battles or whole-game stack use.

## Genuine prior campaign journal

The independently retained Z7 pause-prefix SRAM SHA-256 `182407d91e782c4e879e65047223a70a0ec5f83bbec0131d4e205debddbd0d39` was previously used in an ARM continuation. Its cargo-transport1 slot, sequence, length and checksum passed the existing verifier before import. Both the candidate and painter stayed on HOME after physical L and set the load-error countdown to 89; the exported 32 KiB seed was byte-identical. The diagnostic observed 10,396 untouched painted bytes after that failed load attempt. Thus this particular valid older journal is rejected by this staged reader; its deeper reason is not diagnosed here. The failed load did not reach a campaign continuation or its save path.

An initial new Z7 campaign run on each ROM reached frame 31 and reported the expected pause-menu save failure (notice 188); inputs and named-state fingerprints matched. The backend could not export SRAM from the blank boot because the rejected write had not initialized an SRAM device, so that first attempt is retained as a failed export, not proof of unchanged SRAM. A follow-up booted both ROMs with the genuine custom SRAM from the passing physical continuation. Both drove the same 46 physical step calls to Z7 frame 31 and reported SAVE FAILED (notice 188); their named-state fingerprints matched. Both exported the 32 KiB SRAM unchanged with SHA-256 `9085695f9749b077baffebe8c46b4dbae7c3152ba6322b356c6489b24db1ddee`. The painter observed 10,192 untouched bytes at this refusal. This verifies refusal and preservation for this one seeded point, not successful campaign saving.

The originally supplied legacy backend `0ee4ca…` lacked physical-button mode; the failed startup was retained and not counted. Local private inputs, build commands, logs, physical inputs, journal files and full result JSON are retained in `.local/stack-qualification` of the isolated qualification checkout. Remaining source/stack/codec/performance and full campaign gates are unchanged.

## Source checks

On the staged probe source, the indexed source-boundary check passed (1,789 files), as did `./dev doctor` and `./dev build`. `./dev test` completed with **7 failures and 19 skips in 1,009 tests**; it is not a pass. Four optional canonical-roster subcases lacked the correct private inputs: Terran's managed walk-word header, Protoss P10's fact header, and current Z4/Zerg banks containing raw 85. The renderer qualification separately recovered the Z4/Z6 banks; the remaining Terran/Protoss coverage also requires its correct source-art cover inputs. Two HOST rendering fixtures failed to compile because `hud_panel_clock` and `hud_panel_objective` were undeclared under their flags. The shared-Egg tag registry rejected the staged `SC64_SHARED_ACTOR_SAVE_VERSION` expression.

Those latter three failures were independently reproduced, with the same private inputs, in a clean detached worktree at unmodified candidate `74d0bad0`; the painter source was absent there. This does not excuse or repair the candidate failures. The private header/blob manifest used for the stack probe had zero changes after the full test run. The complete full-suite and unmodified-baseline targeted logs are retained locally, and the candidate remains experimental.
