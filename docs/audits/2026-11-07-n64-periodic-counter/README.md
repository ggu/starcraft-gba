# N64 periodic countdown: bounded writer evidence

A separately qualified observer-only watch used the already instrumented ares core and the same 4,322-step controlled Probe plan. Its fixed watch covers only the five physical RDRAM bytes containing the candidate countdown and adjacent flag; it does not read MMIO or modify guest state. The watched range was armed after the same authenticated 8 MiB baseline and bounded by 96 events. This was one authorized hybrid replay, not a fresh-reset interpreter run or a hardware measurement.

The run returned 0, GPU ready and no recorded overflow. All three RAM views, two frames, 606 actor-store events, 157 entry events and eight stack windows matched the prior control byte-for-byte; two further stack windows were explicitly skipped. The 36 watched CPU stores all came from guest PC `ffffffff80023954`, with opcode `ac825acc`, and their captured opcode and effective-address calculations matched the baseline code and registers. Their stored 32-bit values were 66 through 31, each one less than the previous event. Applying the watched stores to the initial five bytes exactly reproduced both later views: `0000003200` and `0000001f00`. No adjacent flag write occurred in this interval.

The private counter stream SHA-256 is `ec7e74e9ee25c10673277aa615f5e2b8dfc64f0d4ff25d17386e6b027d134c90`, the manifest SHA-256 is `1dff0d59a48551f8b49a8e1cbc954d13dae347fa576d0e048db3c91e5306692e`, and recorded owned output was 60,690,946 bytes before the manifest. Source, binary and compiler dependency checks passed. The private ROM, RAM, frames and event streams are not distributed.

This establishes the actual CPU writer and decrement sequence of a periodic countdown in this replay. It does not prove the enclosing routine executes once per game update, identify an independent monotonic clock, or establish pause, speed, STOP, another actor or hardware behavior. The five previously unexplained final actor-record bytes remain outside the complete CPU-store reconstruction. No timing optimization follows.

A possible future bounded pause/resume control can reuse the same qualified binary and 4,322-step controller prefix, changing only a separately pinned wrapper/plan. Reserve the first RAM view for the authenticated baseline, then use ordinary Start and neutral input to reach a visibly confirmed pause, capture a pause frame/view, issue Start again, and capture a resumed frame/view. Keep the same three-RAM/two-frame and event caps and compare the pre-pause event prefix with this control. Validate the actual on-screen pause and resume before interpreting the countdown: the concrete prediction is no countdown stores during a confirmed paused interval and resumed stores after play visibly resumes; either observation can fail. This does not by itself establish speed scaling or a global game clock. The exact input schedule, trace windows, possible cap exhaustion, source and wrapper must be reviewed and separately authorized before any such replay; no additional run is authorized by this audit.
