# Experimental research stack-usage inspection

This is static compiler evidence, not measured stack high water, a complete call-graph proof, an IRQ safety proof or physical hardware qualification. The examined experimental runtime source is `8a96f99539b6200f67878d935ab51b129ea294f2`. An isolated worktree used the previously qualified P10 and Z9 production vectors plus all four experimental research flags and `-fstack-usage`, GCC `arm-none-eabi-gcc 16.2.0`, the same private inputs and audio bank. The 589 recorded input hashes matched before and after both serialized links; both link guards passed. Separate output paths preserved the qualified ELFs. Objcopy raw binary output matched each qualified ELF byte-for-byte: P10 SHA-256 `d267008fd6cc871405c0521ddce5b2f40547f53c722b3b606edc46d480895cd2`, Z9 `d4c088b92e40df03a783595fe34b249b2986232bf3d767b5e4b5d0941e3178ee`. Qualified input ELF SHA-256 values were `06956233461f23d2f5ba34eaab8af5cfa8e45b193e76564486db01dc2778932f` and `077d736265549b4f47f87ab97cc135fbf6bc0ac44ee23fdad9504d16207c2e7b`, respectively. The build receipt, exact command lines, `.su` files, disassembly and partial call paths remain private under `.local/stack-audit/` and `build/stack-*.su`.

`common/start.s` initializes SYS SP at `0x03007e00` and IRQ SP at `0x03007fa0`; the linker requires `__iwram_end < 0x03005000`. The difference between the SYS initial SP and the link guard is 11,776 bytes. The initial IRQ-to-SYS SP difference is 416 bytes, but BIOS/exception entry, interrupt mode transitions, nesting and any other IRQ stack users must be established before interpreting this as an available C-stack budget. The linker guard is a placement constraint, not an automatically measured stack boundary.

GCC emitted 743 P10 and 696 Z9 `.su` entries, each labeled static; assembly, compiler-runtime routines lacking `.su`, indirect calls, recursion and actual control-flow compatibility are not fully resolved. Largest individual reported frames were P10 `race_p6_save_candidate_valid.constprop` 2,896 bytes and Z9 `race_z7_save_candidate_valid.constprop` 3,240 bytes (`race_z6_save_candidate_valid.constprop` 3,184). These are frames within multi-mission products, not measurements for one specific active mission. Selected research frames were `sc64_pr_job_valid_custom` 56 bytes and `race_research_jobs_candidate_scan.constprop` 176 on both; P10 `sc64_pr_stage_tick` was 72. P10 `race_save_game` was 328, `load_game` 272 and `race_load_preflight_candidate` 232; Z9 was 304, 8, and 192 respectively, with a separate 352-byte `race_load_game`. A static direct-edge inspection of `race_save_game` and its known descendants yields example cumulative reported-frame paths of 3,404 bytes P10 and 3,768 bytes Z9, excluding their callers and unresolved edges. These numbers do not establish the maximum live stack.

The save selection path is particularly easy to undercount: `save_select_prepared` calls `save_prepare_selection`, which invokes the validator through a function pointer; the supplied `race_worker_cargo_prepare_selected` then reaches `race_load_preflight_candidate`. The reported intermediate frames are 112, 32 and 160 bytes respectively. Following that known callback edge and summing the indicated GCC frames gives example structural paths of approximately 4,348 bytes P10 and 4,528 bytes Z9 from `main` through `game_update`, `game_update_step`, result handling, `race_save_game`, the validator and their respective largest inspected candidate descendants. These are conservative sums of reported frames along structurally connected calls; no ordinary run established that every condition on either path occurs together, and unresolved calls or a different path may use more. Tail calls, inlining and callback/assembly transitions require care; no full-stack guarantee follows.

For sampled audio, the reported C frames for `audio_irq` (16), `audio_vblank` (112), `audio_decoder_run` (48), and `audio_decoder_run_p1` (88) total 264 bytes on that inspected path, excluding BIOS/exception entry and unreported assembly. Other decoder paths and `audio_mixer_sum` were also inspected; the relevant interworking veneer has no reported C frame. The backend's interrupt behavior and remaining IRQ headroom need hardware-aware verification. No stack watermark, interrupt nesting test, stack overflow stress, or performance/FPS test was performed. The optional flag-off comparison was not run.
