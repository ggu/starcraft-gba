# HOST-only Z10 compound Flash prototype

This disabled-by-default experiment connects the real shared game save/load codec to the strict HOST Flash model for a narrowly scoped Z10 campaign. It composes worker cargo, the paid Scarab lifecycle, current source-controller identities, and Q8 HP debt. It is not an ARM activation, ordinary-input run, campaign victory, cartridge test, or hardware timing claim. The prior custom 0x48 and P1 0x49 formats and readers retain their meanings; the new compound namespace is 0x4a. Normal ROM flags remain off.

The version-2 record begins with a 32-byte fixed header binding version, profile, mode, mission, feature bitmap, base codec and exact section lengths. It is followed by the actual cargo/impact/transport base, HP debts, current unit/building controllers, per-unit Scarab payer witnesses, and full-width Scarab flight waypoints. For the supported 240-unit, 160-building shape the sections hold 400, 400, 240 and 960 bytes respectively. A conservative prior 16,368-byte base bound yields 18,400 bytes including the header, within the 28,656-byte Flash payload; the mixed-feature maximum still needs an actual capacity proof. The journal streams header, base and tail without a second full payload buffer. Unknown versions, features, profile, codec, reserved fields and lengths are rejected. The checksum checks consistency and is not cryptographic authentication.

The flight section is essential: in this source-cadence prototype, moving Scarabs use `path_timer` and `path_retry` as source waypoints up to 32,767, but the existing compact row allows only 24 and 12. A real moving example had waypoints 716 and 128, and the unchanged compact encoder refused it. The version-2 writer zeroes those narrow fields in an authenticated raw-85 wire row and carries the exact values in the detached section. Candidate-bound decoding restores them before cargo, graph and mission validation. Noneligible entries must be zero; dead Scarab slots serialize as inert zero slots. Version-1 0x4a records are not reinterpreted.

At source `baca45792063ac230bf04b9d2ea4930e4242c8c8`, strict ASan/UBSan HOST tests used the actual Z10 descriptor and save/load paths, with prepared inputs unchanged. The authored setup transfers a descriptor Reaver from source controller 0 to town 7 while preserving raw origin 0, debits that town's 15 minerals once, and refuses transfer while paid work remains. Separate fresh-process readers restore a training child, an inside child, a freshly released child and an already-moving child, preserving the controller, payer, wallet and a half-HP debt produced by an actual shared damage packet. The moving case compares parent fields, child carry/fraction, timer, order, target, coordinates, both waypoint and path pairs, weapon, full 16-bit cooldown, controller, payer, HP debt, wallet and frame. Original and fresh-loaded processes then advance the real child and impact services to the same hit, retirement and selected outcome. The initial save/load defect that copied encoded rather than decoded child rows was fixed; the earlier moving-row refusal and its diagnostic are retained in private logs.

The same run exercised checksum-valid invalid-controller and invalid-unused-flight rows with no failed-load publication, fallback from a semantically invalid newer record to an actual older 0x4a record, and failed-save snapshots of actors, controllers, debts, research levels, impact queue, Yamato shots and wallets. A stale Yamato reference remains unchanged on a rejected compound save: this stage skips pre-save live reconciliation and relies on candidate rejection. Bad-checksum unknown/v1 raw headers are refused before erase or program. A genuine retained version-1 HOST image, SHA-256 `e80794c9f76891c237a0ffee6c990dd92faabd85785ae57c52e61d28537f22ae`, was also refused without modifying its bytes. These deliberately malformed records are test fixtures, not genuine predecessor evidence.

The first 32 KiB is required to be entirely blank and is never programmed or erased by this stage. Existing 0x43/0x44/0x47 legacy records and 0x48/0x49 Flash records are fenced rather than migrated; genuine Z10 predecessor loading remains unqualified. Unknown committed or metadata-owned 0x4a tuples block a new write even when their length or checksum is bad. This conservative rule has an explicit recovery gap: the journal programs metadata before the envelope header, so a failure between them leaves an erased commit with incomplete metadata-owned content. A real injected program failure at that point preserved the live snapshot; a fresh process refused both load and subsequent save without further writes. Safe identification/recovery of this ambiguous partial record is not solved, so crash-safe gameplay integration is not claimed.

The same frozen run passed the existing P1 producer/fresh-reader and P1 stale-descriptor/epoch/read-I/O fault cases, the strict Flash model including three-part streaming, and source boundary. The test receipt SHA-256 is `30198ccc88c2c11559ce8df3bdcb8eb7fe00a9a77f177b4b119040ed9ffbe751`; 593 prepared private input hashes were checked before and after. Representative private images have SHA-256: training `721c61bb7ff2e3fd59955ecfea62d41e0e59ac585c8628085c8e67d9a0f098ec`, moving `8c2a9bfb136612883fd75ae1ab1214c12ecfcd1212c0a259700f4a274ef101a0`, and interrupted write `d019a05b9aee0443a31aa26c34f0de1f64ecce5f607eaab9ec8d4430b89673ae`. The images, private inputs, and logs are not committed.

The public optional recipe is `make -f Makefile -f tests/sc64-zl-scarab-controller/Makefile SC64_AUDIO_DIR=<prepared-audio-dir> ZL_SCARAB_COVER_DIR=<prepared-cover-dir> CONTROLLER_FLASH_POLICY_DIR=<prepared-policy-dir> test-zl-scarab-compound-flash`. It requires already prepared private inputs and generates none. The additional `test-zl-scarab-compound-v1-fence` target takes `COMPOUND_V1_IMAGE=<verified-prior-image>` after the main target builds the fixture. All native work must use the project's shared lock and disk guard.

Still open: genuine old-format migration and fallback, ambiguous partial-write recovery, maximum legal actors/impacts/transport and active research combinations, other campaigns and custom profiles, stronger atomicity and collision analysis, aggregate stack and ARM memory guards, ordinary guest behavior, flash-device identification/timing and physical hardware. The existing stage is not a full campaign or release qualification.
