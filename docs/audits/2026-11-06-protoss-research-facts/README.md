# Protoss research: authenticated facts and integration boundary

At runtime source `31a5ddf8d3734427ebfef151acfb683d0db54a03`, the WEAPONS and ARMOR rows use SIDE-only generic globals, require a Forge for Protoss, charge 100 minerals and 100 gas, finish after 600 updates, and stop at level two (`starcraft/game.c`, `start_research` and `tick_research`). `RaceSave.state` stores those four generic values. This does not represent Protoss upgrade families, other owners or producer identity. The stock-weapon helper already has a source per-impact `upgrade_bonus`; some other attack and shield paths use separate calculations and cannot be covered by changing the menu alone.

`tools/sc64_protoss_research_facts.py` authenticates the owned USA ROM, the pinned extractor file (`sc64-maps` commit `09b57f787a247107d1de82b8c5eab2734667ea1d`, file SHA-256 `6a84761a9a8074fcc393527a7b17cea194084e8ab49176ff82fa3bef8e1b1dc2`) and the private N64 `upgrades.dat` entry `00C/006` (SHA-256 `5c7a104f37eab018d15719066052c2db25ef046d9330770045d7e4977f98c12b`). It prints only six selected numeric rows. For level n, cost is base + factor × (n−1), separately for minerals and gas; source time is base + factor × (n−1):

| Upgrade | Source id | Mineral and gas base | Each level increment | Time base / increment | Maximum |
| --- | ---: | ---: | ---: | ---: | ---: |
| Ground armor | 5 | 100 / 100 | 75 / 75 | 4000 / 480 | 3 |
| Air armor | 6 | 150 / 150 | 75 / 75 | 4000 / 480 | 3 |
| Ground weapons | 13 | 100 / 100 | 50 / 50 | 4000 / 480 | 3 |
| Air weapons | 14 | 100 / 100 | 75 / 75 | 4000 / 480 | 3 |
| Plasma shields | 15 | 200 / 200 | 100 / 100 | 4000 / 480 | 3 |
| Singularity Charge | 33 | 150 / 150 | 0 / 0 | 2500 / 0 | 1 |

These are source-table units, not verified N64 runtime durations. The project's existing 5:4 frame-conversion policy is an approximation and must be applied explicitly, not described as native timing. [Pinned BWAPI upgrade types](https://github.com/bwapi/bwapi/blob/d727fed68558c506163048ea889131d8cbb33915/bwapi/BWAPILIB/Source/UpgradeType.cpp) identify Forge for ground weapons, ground armor and shields; Cybernetics Core for air weapons, air armor and Singularity Charge. Its requirement table is a PC-source proxy, not an authenticated N64 prerequisite trace. Producer validity, power interruption, cancel/refund and scenario-specific upgrade limits require independent treatment.

A bounded production implementation needs per-owner level and paid job state, an exact producer binding and family uniqueness checks; real payment, completion, and field UI must all share the same rule source. It must use the authenticated weapon upgrade ID to choose weapon family and the unit armor upgrade ID for armor; shield upgrades apply in shield damage. Neither target nor attacker flight alone is a sufficient weapon-family discriminator. Singularity must change the relevant Dragoon weapon range rather than all ranges. Validate each route against source weapon/armor identities and special-unit handling.

The existing save stores two generic SIDE-only levels and timers; loading an old journal must not silently reinterpret a generic weapon or armor level as one family only. A new authenticated version and explicit legacy policy must preserve or deliberately migrate both ground/air effects and pending generic jobs without awarding shield upgrades. Candidate validation must happen before mutating the live world, reject duplicated or invalid producer bindings, and preserve journal fallback. `RaceSave` has profile-dependent layout and `common/gba.h` limits accepted journal tags; capacity, tag collisions and actual EWRAM/IWRAM/stack guards must be measured for every supported product before selecting a wire layout. No save-schema change or runtime research implementation has been made in this facts-only checkpoint.

## Bounded wire candidate (not integrated)

The first 120-byte job-wire sketch does not fit the reported 16,312-byte Z7 v36 payload in a 16,368-byte journal slot. `sc64_protoss_research.h` now tests a separate 12-byte completed-level codec (48 two-bit values for eight campaign source slots, or five custom runtime owners plus three canonically zero slots), leaving 44 bytes of that particular reported slack arithmetically. This is not a link or stack qualification. A possible active-job representation stores family and remaining ticks in the already serialized `Building.level` and `Building.queue_progress` of each completed Forge or Core; producer slot and owner derive from that building. Both Z7-derived and P7-typed 25-byte rows preserve these fields, as do packed and s16 rows. BC lab research uses the same fields for another raw type. This proposal requires proofs that raw 164/166 aliases cannot simultaneously own any production queue or another service, and that all supported codecs, resets, deaths, slot reuse, construction transitions and candidate validators preserve the invariant. Never reinterpret old live values without a new authenticated format.

For a legacy Protoss human, a candidate migration must preserve the previous generic bonus on both ground and air weapon families and both ground and air armor families, without inventing a shield level. Pending old generic jobs need their original completion timing and payment preserved; blocking conflicting new family jobs while they finish is one possible policy. This is not yet an implemented or tested migration. Legacy non-Protoss generic behavior and unrelated owners must remain intact. New-format records must bind every active job to a completed valid producer and reject duplicate family-per-owner jobs before live state changes. Canceled/destroyed producer handling, paid refunds, power-loss behavior and crash recovery remain unresolved.

The normal shared-transport reader currently accepts two cargo tags; retaining both and adding their two research generations would use four of the five accepted tags. Combined staged Guardian/Egg readers already use five. This observation is not a guarantee that a new bit or tag is collision-free, nor that every profile and rollback path supports it. Any extension must audit all active tags and choose the newest valid record across old and new generations, including malformed-new/valid-old fallback. No journal writer, reader, UI or combat path currently uses this helper.

## Source owner and weapon association

The campaign's CHK UPGR format has 12 source rows, but the current engine maps active campaign player slots 0–7 and treats slots 8 and above as neutral in its general owner resolver. P7 explicitly validates eight raw slots, with the human in raw slot 7 and distinct source computer slots potentially sharing runtime `ENEMY`. Those distinct raw source identities cannot use a single enemy upgrade level. Custom play instead has five compact runtime owners. The helper accepts these contexts explicitly and rejects nonzero unused custom slots. This storage shape alone does not establish that all source-created actors retain authenticated raw-owner provenance or that all campaign UPGR/UPGS overrides are imported; both are required before live use.

The owned `units.dat` and `weapons.dat` tables are independently authenticated by the facts tool. For example, Dragoon raw 66 uses weapon 66 and upgrade family 13 against either ground or air; Scout raw 70 uses family 14 against both; Interceptor raw 73 uses 14; Scarab raw 85 uses 35; Probe raw 64 uses raw upgrade ID 60. The latter is outside the six proposed Protoss families; this observation alone makes no broader claim about its native behavior. The current stock runtime table lacks weapon upgrade IDs, so the mapping must be represented explicitly and tested before combat integration.
