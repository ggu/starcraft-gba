# Candidate-local Guardian and Egg authentication

The existing Guardian-only HOST prototype uses `race_guardian_stage_wire` in capture, selected-candidate preflight and publication. A later selected slot can overwrite that global while another candidate's detached data or prepared plan is still being inspected; an old-tag record must never acquire Guardian interpretation from that state. The current compile guard deliberately forbids enabling Guardian and shared-Egg wire stages together.

The selected journal callback must reset a candidate-local plan, authenticate exact outer/inner tag pairs only after the selected slot passes checksum validation, and retain the unchanged inner discriminator. A decode context must bind the exact candidate address and allowed Guardian/Egg feature bits; ordinary wrappers carry no staged authorization. The trusted live capture path needs its own explicit writer context, rather than borrowing a selected candidate's context. The context must reach the top-level unit preflight and each active nested validator (battery, bunker, transport, mission, carrier and shot services as applicable), and the publication loop must use only the plan selected by the journal. Failure or candidate replacement must reset the plan. Appended Egg IDs use stage-specific six-bit codec admission; legacy entrypoints remain strict. Ordinary Overlord/raw36 records must remain distinguishable from an authenticated staged Egg by explicit type and tag.

A successful implementation must exercise actual checksum-validated prepared journals and real profile codecs for the canonical four products, including legacy, Guardian, Egg, and combined contexts, cross-candidate interleaving, bad-newer/good-older fallback, half-range ambiguity, unknown tags and unchanged live world on failure. Registry collision tests alone prove only tag separation. No default/guest flag is enabled by this plan.

## HOST-only combined candidate under development

`SC64_GUARDIAN_EGG_CANDIDATE_HOST_STAGE` is a separate explicit HOST/custom journal experiment; merely enabling the two feature flags continues to fail compilation. Its proposed selected-slot table contains the legacy worker-cargo, current, Guardian, Egg and combined outer/inner pairs. The selected plan binds one context to the detached candidate; Guardian/Egg normalization, preflight and publication use that context. Capture chooses the combined tag only in custom games, with Guardian-only staging otherwise. No guest, menu or default flag enables this path.

The combined Egg validator derives active owner/race mappings from the candidate's saved custom-game fields, validates raw36 Egg/product/timer fields and catalog membership, and counts building queues plus the extra body of each paired Egg against free slots. Where Carrier training is compiled, its already-paid additional-body count is `carry`; the already allocated training child remains a live unit and is not counted again. Scarab runtime and Scarab namespace remain compile-fenced because their competing reservations are not integrated. Trigger reservations remain outside this custom-only combined experiment.

`tests/sc64_guardian_egg_combined_journal.c` is intended to exercise all four canonical profile codecs and actual selected journals with legacy, Guardian, Egg and combined feature contexts, ordinary Overlord/raw36, exact outer/inner mismatch rejection, bad-newer/legacy-older fallback, and a P10 Carrier-plus-paired-Egg reservation boundary. All constructed records are HOST fixtures. As of this note these combined paths are **uncompiled and unqualified**: the first attempted run stopped at the disk guard before any generator or compiler started. The live Guardian-only four-profile evidence and mixed legacy/Guardian fallback are separately scoped and do not qualify this combined path.
