# Pinned ares JIT-to-interpreter feasibility

This is source-only analysis of ares `0aafd85789215e84e1e43415c07d4c88461b7899`. It does not authorize or claim a new run, fabricated state, modified guest memory or a timing result.

The official node interface exposes `serialize(bool)` and `unserialize(serializer&)` (`ares/ares/node/system.hpp:10–11`), and the desktop state-save/load path calls them (`desktop-ui/program/states.cpp:11,28–36`). N64 `system/serialization.cpp:3–35` records a signature and serializer version, optionally powers the system before restoration, then restores serialized components including RDRAM, CPU and RSP. `cpu/serialization.cpp:15–28` includes instruction-cache tags and words and data-cache tags, dirty flags and words; it also serializes pipeline/register state and resets the compiled JIT cache at lines 135–137. `rsp/serialization.cpp:57–59` resets the RSP compiled cache. A state created by ordinary input and restored by these official APIs is a legitimate emulator state operation, not guest-memory fabrication. It is still a savestate-based observation, not a fresh-reset reproduction or proof of continuous native timing. A state file can include at least the 8 MiB RDRAM payload and needs explicit existing-budget accounting; an in-memory operation avoids claiming an output-file exception but does not prove time or memory feasibility.

The `Recompiler` option immediately changes both CPU and RSP enabled flags (`system/system.cpp:38–44`). CPU instruction dispatch selects the JIT or interpreter at `cpu/cpu.cpp:145–172`; RSP does the same at `rsp/rsp.cpp:48–59`. The desktop N64 frontend applies the option before `Nintendo64::load` (`desktop-ui/emulator/nintendo-64.cpp:107–121`); the setter itself has no explicit stop, synchronization or cross-mode validation. Source therefore establishes an accessible option, not a documented safe live-switch contract. The CPU JIT's cached memory path refers to the same data-cache line structures and sends misses to its slow path (`cpu/recompiler-ipu.cpp:147–164`), but this alone does not establish coherency for every operation or safe mode transitions.

A bounded future experiment would first require separate review of a switch at an owned `root->run()` return boundary, actual CPU/RSP flags, cache-hit/miss reads with the existing conflict guards, and independent state/ordinary-input comparisons before and after; a serialization route also needs verified renderer/VI continuity and complete provenance. No RDRAM write, cache bypass, unsupported clock, state injection or increased step/output/wall budget is implied. A single hybrid result cannot certify reset-to-observation behavior, order cadence, writer PC, or timing. Whether either route reaches a useful point within 175/180 seconds remains unmeasured.

## Synchronized same-process candidate and graphics limits

The narrowly scoped candidate is: fresh ordinary-input play in the owned process with official CPU/RSP JIT; at a returned `root->run()` boundary call the official `root->serialize(true)` in memory; set the official `Recompiler` option false; restore that exact unmodified in-memory serializer with `root->unserialize`; verify both CPU and RSP flags remain false; then continue ordinary inputs with the existing read-only cache-aware observer. No externally supplied/constructed state, state file, guest memory write, CPU cache bypass, or expanded budget is implied.

In pinned N64 source, `serialize(true)` writes the boolean and serializes component state, but `System::serialize(serializer&, bool)` at `system/serialization.cpp:39–60` does not call `CPU::synchronize` or an explicit Vulkan drain. A returned owned run boundary is a testable precondition, not a source proof that all GPU work is quiescent. On restore the saved true flag calls `power(false)` first (`system/serialization.cpp:20–35`): `system.cpp:427–451` unloads Vulkan, marks it for reload, powers components, and then the serializer restores their saved state. The next `System::run` reloads Vulkan (`system.cpp:81–86`). RDRAM, VI, and RDP component fields are serialized, but the component list contains no Vulkan implementation or parallel-RDP GPU-context serialization. Exact pre/post graphics continuity therefore remains unproved; do not assume a restored Vulkan context is identical to the old one.

The CPU and RSP recompiler `reset()` methods clear their compiled-block data without setting `enabled` (`cpu/cpu.hpp:1100+`, `rsp/rsp.hpp:644+`), and those enabled flags are absent from their serializer lists. This supports the proposed option ordering at source level, but the resulting flags must be checked after power/restore and before inspection. CPU serialization carries cache line tags, dirty bits and words. The minimum useful test must compare the same bounded cache-aware views and conflict results immediately before the in-memory serialize and immediately after restore, then perform controlled continued ordinary input and compare visible framebuffer/UI against an independently observed control. An alias conflict, failed restore, graphics mismatch or timeout leaves the route unqualified. Account for all private output within the same 64 MiB allowance and existing process limits; an in-memory state avoids a file-size exception, not a performance or memory guarantee. This is an authentic hybrid restore experiment, not full fresh-interpreter execution, native actor identity, writer-PC or cadence proof.
