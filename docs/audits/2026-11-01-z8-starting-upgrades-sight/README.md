# Z8 starting upgrades and sight

This source-only audit reads the retained authenticated Z8 CHK from catalog entry `008/01B`. `tools.sc64_zp_scenario_pack.parse_source` verified its manifest and SHA-256 `ff6d0177a6a76fc68ef98f0962661857853ea11c50de9060b90ff934826cfd8e`. The pinned USA ROM SHA-1 is `a36d91b5aac7bb95df0d7de5f9814f5270e25c2b`; the source foundation records extractor revision `09b57f787a247107d1de82b8c5eab2734667ea1d`. No raw CHK or source asset is included here.

For active source slots 1, 2 and 3, every one of the 46 `UPGR` upgrade cells and 61 `PUPx` cells uses its global default, and each resolved initial level is zero. Both decoded sections agree for these owners and the first 46 IDs. In particular owner 3 Ventral Sacs (24), Antennae (25), and Pneumatized Carapace (26) start at 0 with a maximum of 1; relevant Zerg and Protoss weapon, armor and shield upgrades start at 0 with maximum 3. `UPGR` was decoded with the existing `tools/sc64_z6_transport_pack.py:decode_upgr`; `PUPx` was read using the same player/default/selector layout extended to 61 entries. The sections do not have identical inactive-owner defaults. The local audit did not establish which section the N64 loader selects; the active-owner result agrees under either decode. No conclusion about upgrades earned later follows from starting levels.

The campaign initializer sets the existing generic human weapon and armor levels to zero. Its Z8 Overlord follows the unupgraded stock motion path: raw 42 has Q10 source speed 850 and `sc64_stock_runtime_speed_q10` yields 340/1024 game pixels per engine update on a cardinal axis. Therefore the recorded slow Overlord flight is not explained by an omitted starting Pneumatized Carapace upgrade. This does not establish acceleration, turning, later upgrade acquisition, or native AI fidelity. Z6's Ventral Sacs runtime and menu are gated to Z6; Z8 does not gain that later research route merely from its source maximum of 1.

There is a separate sight discrepancy. The shared pinned BWAPI source-sight table (`starcraft/sc64_source_sight_tiles.h`, revision `d727fed68558c506163048ea889131d8cbb33915`) gives an unupgraded Overlord nine source tiles, or 144 game pixels at the project's half-map scale. The pinned OpenBW `unit_sight_range` uses 11 tiles only with Antennae; its detection routine uses a mobile detector's sight range and caps grounded building detectors at seven tiles. Current Z8 special Dark Templar detection instead hardcodes an Overlord radius of 176 game pixels and a Spore radius of 112; meanwhile the ordinary visibility source-sight helper is gated to Z7, and ordinary Z8 Overlords fall through to the 72-pixel generic visible radius. These are separate visibility and detection paths, not evidence of one consistent source radius. OpenBW uses unit-to-unit distance and additional detection eligibility checks; the current center-distance approximation is not proven equivalent. Neither this PC reference nor these source table facts establish the N64 handler's exact geometry or palette-independent visual behavior.

A minimal candidate should reuse `sc64_source_sight_raw_pixels` and existing actor-specific fact precedence for Z8 ordinary visibility rather than copying nine-tile constants. Apply the same source identity to Z8 Overlord detection, preserving the current validated Spore completion and seven-tile policy while separately qualifying distance geometry, disabled/blind state and visibility interactions. Handle unfinished building visibility keys and cache add/remove transitions explicitly; do not change Z7 or other mission behavior by accident. Keep Antennae at its authenticated initial level and do not invent an upgrade grant.

Before enabling such a change, test source fact selection for raw 42 and other mapped actors, Z8 versus Z7/profile isolation, Overlord visibility and detection boundaries, Spore completion, hidden and loaded units, movement across visibility-cell edges, and save/load reconstruction. Compare the optimized visibility path against its scalar oracle for overlap/removal, camera and fog transitions. Use ordinary controls on the actual corrected-clock Z8 profile and requalify the affected controller path; capture ARM memory budgets and a bounded performance window. Existing Z8 losses and earlier Z7 ROM proofs do not prove the candidate or a mission win. Direct N64 detection behavior remains an explicit evidence gap.
