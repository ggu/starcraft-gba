## 1. Projectile lifecycle: captured endpoint, no following or bounce (high impact; high confidence current code, medium N64 behavior)

`starcraft/game.c:4551-4569,8185-8205,10641-10665` saves launch and target coordinates in a cosmetic tracer and draws from those fixed endpoints. `starcraft/sc64_impact_adapter.h:77-102` computes a one-time delay for fly, follow and bounce classes alike; `starcraft/sc64_weapon_source_runtime.h:104-107,137-142` explicitly uses straight distance and does not simulate turning, homing, collision or bounce. The pending hit remains bound to the live target even if it has moved, so the drawn impact can land at the old position while damage is applied elsewhere. A bounce-class shot receives just the ordinary single-target packet; generic Mutalisk bounce damage is absent. This affects both visual readability and combat, broadly across mobile-unit battles.

N64 source evidence: `docs/IMPACT-EVENTS.md:28-40` records authenticated ROM weapon bullet types, flingy speed/acceleration, release and Death `domissiledmg` records; all moving profiles have that damage event at Death tick 0. `docs/IMPACT-EVENTS.md:42-49` explicitly labels following as the OpenBW interpretation; N64 runtime movement/bounce and targeting are not traced. `docs/native-weapon-effects.md` additionally records Scout's two source bullets with alternating initial heading offsets, currently drawn on coincident paths. Existing mGBA impact replay proves the existing queue behavior and save continuity, not native homing or bounce.

Isolated next step: trace/observe a moving-target follow missile and a Mutalisk attack on clustered targets on N64; implement bounded shared projectile state and per-projectile target/position/lifetime with explicit save, slot reuse and overflow policy. Start with follow-type flight; add bounce only with evidence of target selection, falloff and limits. Acceptance: moving-target visual impact and damage coincide, independent Scout shots visibly separate, verified bounce targets/damage, dead/hidden/reused target behavior, save/reload equivalence, all prepared profiles and crowded ARM timing/RAM checks.

## 2. Weapon release and impact are not one source-driven lifecycle (high impact; high confidence current code, medium timing interpretation)

`starcraft/sc64_impact_adapter.h:82-87` only schedules moving bullets; `starcraft/game.c:8199-8214` applies the remaining generic attacks immediately, even while source attack art is still winding up. `docs/IMPACT-EVENTS.md:323-327` documents appear-at-target shots 3–8 updates before their depicted source wind-up/impact, while melee and appear-at-source are also immediate. Hits can kill/remove a target before the visible attack lands. Two-shot packets are merged, rather than resolved at each shot's event. `docs/native-weapon-effects.md` says the source animation is a linear extracted path, without random branches, calls, repeat conditions or complete interpreter.

N64 evidence: the same authenticated IScript bank contains attacker `attackwith`, `attack`, `attackmelee` release and projectile `sigorder`/`domissiledmg` events (`docs/IMPACT-EVENTS.md:28-40`). Exact execution and N64 melee ordering are untraced. The 3–8 updates are the existing bank/PC-proxy-derived comparison, not measured N64 video. The historical native-weapon-effects statement that all damage is immediate is stale for moving shots; current impact queue supersedes it.

Isolated next step: extend shared pending-event scheduler to source release/impact events for target-position/stationary and melee profiles, preserving independent hit packets, attack interruption semantics and bounded save compatibility. First identify which event actually applies damage per weapon and compare N64 captured sequences. Acceptance: frame-by-frame weapon-specific launch/impact and HP/death timing for melee, stationary and two-shot profiles; target death, interruption, shields, pool pressure and SRAM continuation; mGBA profile/memory qualification.

## 3. Construction completion discards the materialization lifecycle (medium-high impact; high confidence current code, medium N64 behavior)

The renderer runs layered source art only inside `q->under_construction` (`starcraft/game.c:11206-11253`); after the existing timer clears that state it immediately renders the completed structure, with no separate late warp/materialization state. The bank and source anchor already exist: this is not a missing-all-construction-art report. `docs/audits/2026-10-26-construction-lifecycle/README.md` records source construction art across 50 identities and an actual-engine Pylon regression (563 updates, 70 changes); it also explicitly says late Protoss warp states, finish signals, worker animation and Assimilator geyser underlay remain incomplete. `docs/VALIDATION.md:4653-4655` confirms the anchor is selected while later materialization is incomplete.

N64 content evidence: the authenticated ROM includes source construction IScript and Warp Anchor image 211. The order transition to completed-building WarpIn and texture materialization is inferred from pinned OpenBW in the lifecycle audit, not independently traced N64 execution. No claim about exact N64 finish duration or which layer/attachment is visible without additional reference capture.

Isolated next step: trace Pylon and Assimilator completion in installed N64 and map the source WarpIn/attachment records, then add a bounded shared completion presentation state without breaking buildability, save/load or power timing. Acceptance: anchor-to-materialized sequence and Assimilator underlay match reference at equivalent phases; no one-frame complete-art pop, save/reload mid-transition, clipping and all-race/profile tests. Separately, damage-fire overlays are already present (`game.c:11199-11204`); `docs/BUILDING-DAMAGE.md` documents their approximated blending, random allocation history and first-pose anchors.

## 4. Shields absorb damage invisibly (medium impact; high confidence current code, low confidence exact N64 effect)

`starcraft/game.c:4782-4788` subtracts shield and returns when fully absorbed, with no shield impact effect in that path. This means hits on shielded Protoss can produce no target-side reaction besides the bar. `docs/ENGINE-FIDELITY-AUDIT.md` independently records the missing directional overlay and cites pinned OpenBW's impact generation; bar drawing is a separate feature. Special splash/spell paths need auditing too before assuming coverage.

N64 evidence is insufficient to assert the visual mapping: neither image ID, direction, blending nor lifetime is traced in the existing audit; OpenBW evidence is a PC proxy, not N64 proof. This is a verified current presentation omission and a candidate parity gap, rather than a verified exact N64 defect.

Isolated next step: locate authenticated N64 shield image/IScript and compare N64 recordings for attack angles and weapon types; route qualifying absorbed damage through one bounded transient effect API shared by normal and specialized hits. Acceptance: correct source image, location/direction, clock, clipping, palette modifier and visibility; fully absorbed, overflow, invincible, simultaneous and splash hits; bounded crowd behavior and no save-state dependency.
