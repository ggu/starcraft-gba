## Forward-command source inspection

The revision called `order(slot, MENU_ATTACK, 1390, 1810)` for each of the three Hydralisks. The helper selects exactly one unit using L, opens B, chooses the attack menu row, moves the cursor, and presses A. It did **not** choose the Move menu row. Its return value confirms the helper reached the final key press; it does not itself assert the resulting order or target.

This profile enables `SC64_DIRECT_ATTACK`. In `game.c`, the attack menu arms `MODE_ATTACK`; its A handler first searches for a visible, hostile valid target near the clicked cursor position. A unit can be chosen within 31 pixels or a building within 26; the closest eligible entity becomes an explicit `ORDER_ATTACK_TARGET`. Only if none is found does the same attack-mode click issue `ORDER_ATTACK_MOVE`. By contrast, the Move menu arms `MODE_MOVE`, whose click issues `ORDER_MOVE`. Therefore the observed attack-target orders are consistent with the controller's chosen command resolving contextually to a nearby enemy, rather than evidence by themselves of an engine defect.

The retained revision log records command completion frames and later unit order/position, but not the exact click coordinates, `target` indexes, target raw IDs/owners, or selection at the later samples. The Dark Templar itself was still hidden and distant from the clicked area at these times; the logs do not establish which other actor or building was targeted, whether all three targeted the same entity, or why the orders remained near their positions. No mission rerun or additional instrumentation was performed for this inspection. A future legal-input policy intending pure repositioning should explicitly choose `MENU_MOVE` and verify the resulting order, while maintaining separate combat commands as needed.
