# Port-free skirmish ARM replay

`tools/sc64_headless_replay.c` runs the supplied production ROM in an mGBA
core with in-process hardware breakpoints. The Python skirmish replay feeds the
ROM's existing windowed input scheduler and checks the resulting configuration
and trace observations. The backend accepts writes only to the five scheduler
symbols passed from the ELF. Use a fresh private HOME and output directory.
Headless reads are restricted to EWRAM, IWRAM and loaded ROM; MMIO and SRAM are not read,
and HOME screenshots are omitted. The pinned 0.10.5 `rawRead8` uses `GBAView8`;
its RAM and in-bounds ROM paths read memory with no timer or I/O register access.

The local reference build uses mGBA 0.10.5 at commit
`26b7884bc25a5933960f3cdcd98bac1ae14d42e2`, configured as a static GBA-only
library with `USE_DEBUGGERS=ON`, `USE_GDB_STUB=OFF`, `M_CORE_GB=OFF`,
`BUILD_QT=OFF`, `BUILD_SDL=OFF`, `BUILD_STATIC=ON`, `BUILD_SHARED=OFF`,
and optional compression, graphics, scripting, and database features disabled.
Use the headers generated by that same build: its compile definitions affect
the core structure ABI. For example on macOS, with the private mGBA checkout
and build at `$MGBA_SRC` and `$MGBA_BUILD`:

```sh
clang -std=c11 -O2 -DM_CORE_GBA -DUSE_DEBUGGERS -DBUILD_STATIC \
  -I"$MGBA_SRC/include" -I"$MGBA_BUILD/include" \
  tools/sc64_headless_replay.c "$MGBA_BUILD/libmgba.a" \
  -framework CoreFoundation -o sc64-headless-replay
```

Linux does not use the macOS CoreFoundation framework; use the matching mGBA
build's link dependencies instead. Record the source commit, configure cache,
compiler, library hash, runner hash, ROM and ELF hashes, and trace hash when
using the measurements as evidence. Private source assets and ROMs remain
outside version control.

For a completed host trace, use `tools/sc64_skirmish_controller_replay.py`
with `--trace`, `--rom`, `--elf`, `--output`, `--headless-runner` and
`--full-per-update`. A bounded prefix instead uses `--sample-start` and
`--sample-updates`, and is explicitly nonterminal. The supplied ELF must match
the ROM, including scheduler symbols and entity DWARF layouts.

Timing is the delta of `mTimingGlobalTime`, in emulated CPU cycles, between
successive `game_update` entries. It includes main-loop work, audio, rendering,
and presentation waits; it is not isolated update or rendering time. The
terminal endpoint is the scheduler checkpoint. Menu, nonadvancing PLAY, and
outside-PLAY intervals are recorded separately from the advancing PLAY mean.
Terminal parity is limited to fields present in the host trace: configuration,
frame, result flags, and active human/bot live entity counts. Other live-bank
fields are recorded observations, not host-verified parity. An mGBA result is
not a physical-hardware measurement.

The host trace numbers input updates starting at one. The injected scheduler
numbers the corresponding updates starting at zero. Thus observation row N
is taken after host update N, which consumed scheduler input N−1; recorded
host-frame comparisons use row N and require no shift.


## Pinned baseline observations (2026-10-29)

Runtime `8d1e653` and the corrected controller's Terran-product traces were
replayed with the pinned mGBA library above and frozen observer sources. The
runtime C/header hashes, consumed generated-header hashes, ordered per-TU
compile commands and linker inputs are retained with the private ROM evidence.
The exact observer/library/configuration, ROM, ELF and trace hashes are retained
with the replay evidence; no private artifacts are tracked in this repository.

| Workload | Advancing PLAY frames | Guest cycles | Effective fps |
| --- | ---: | ---: | ---: |
| Authored map 0, Terran human, one AI, complete loss | 9,601 | 5,642,613,753 | 28.55 |
| Same ROM, map 0, Terran human, three AIs, late prefix window | 1,000 | 599,758,448 | 27.97 |

The complete one-AI replay matches terminal frame 9,603, both result flags,
configuration and participating live entity counts. Its first and last 1,000
advancing-frame windows measure 29.65 and 27.25 fps. Its 46 nonadvancing PLAY
updates, 18 menu updates and one outside-PLAY update are reported separately.
The three-AI window covers completed host updates 8,001 through 9,000; it is
not a completed-match result. These are narrow baseline workloads, not a claim
that all race profiles, campaigns, maps, armies or AI permutations meet 30 fps.
No runtime optimization was made to obtain these numbers.
